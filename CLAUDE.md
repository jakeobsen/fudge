# CLAUDE.md

Guidance for AI coding agents working in this repository. User-facing docs are in README.md.

## What this is

Fudge is a keyboard launcher for macOS, built to run extensions written for Raycast's `@raycast/api` without changing them. It is a native Swift app. Extensions run in a separate Node.js process, the extension host.

## Architecture

- **One Swift package, three targets.**
  - `FudgeApp` is the app: an accessory app with a menu bar item and no Dock icon. The item's glyph is `MenuBarIcon`, a fudge cube drawn in code as a template image. Its autosave name is `fudge` (`AppDelegate.statusItemName`), because macOS keeps whether a status item is shown in the app's preferences under that name, and an unnamed item's `Item-0` was once saved as hidden. It's shown at every launch, and its `behavior` is `[]`, so ⌘-dragging can't remove it.
    - **Global hotkeys** go through Carbon (`CarbonHotKeys` in `HotKey.swift`), which needs no Accessibility permission: one event handler, one id per registration. `HotKeyRegistry` (core) decides what's registered: the launcher's hotkey (`hotkey` in `settings.json`, default ⌥Space, read and written through `FudgeSettings.launcherHotkey`) and each installed command's (`commands` in `settings.json`, by `<extension>/<command>`), registering only what changed. A refused change of the launcher's hotkey registers the old one again (`setLauncher`); one refused at launch stays wanted, marked `launcherRefused`, and is tried again on every `resume`. A change that's registered but can't be saved puts back exactly what was there, the old hotkey registered or still refused (`changeLauncher`), so the registration and the file never disagree. `AppDelegate.launcherHotkeyChanged` shows the outcome on the General page and in the menu bar item's "Open Fudge (…)" title. Hotkeys of commands that aren't installed stay in the file but aren't registered. `HotKeySpec` (core) is the text form (`option+s`, `f5`, `keycode:<n>` for keys with no name), and an F-key may stand alone. `FudgeSettings` reads `settings.json` tolerantly, and writes it atomically, keeping keys it doesn't know. A pressed command hotkey calls `LauncherModel.openFromHotkey`, which follows `HotKeyLaunch` (core): open it as root search would, hide the panel when it's the view command on screen, or show root search with the fields when a required argument is empty. A no-view command run by hotkey doesn't clear root search when it finishes (`LaunchOrigin`). Root-search rows show a command's hotkey as keycaps (`Keycaps`, labelled as the current keyboard layout types the key).
    - `LauncherPanel` is a non-activating `NSPanel`: it takes keys while the app you were in stays frontmost. It opens a little above the middle of the screen **Show Fudge on** picks (`showOnScreen`, `PanelScreen.choose` in core): the mouse's (the default), the primary one, or the one holding most of the frontmost app's topmost window, read with `CGWindowListCopyWindowInfo`, which needs no permission for bounds. Its bounds are flipped to Cocoa coordinates first (`PanelScreen.cocoaFrame`), and with no such window it's the mouse's screen.
    - **Esc** follows `EscapeAction` (core) and **Escape Key Behavior** (`escapeBehavior`). An open dropdown or action panel closes first either way, then the Quick Look preview. "Navigate back or close window" (the default) pops a view, clears the search, leaves the command, then hides; "Close window and pop to root" hides at once and resets to root search as Pop to Root Search does. A Form keeps navigating back, since Esc is its own key there, and Esc in an argument field, an input method, a hotkey recording or an alert sheet never reaches `LauncherModel.escape()`.
    - **Pop to Root Search** (`resetAfterSeconds` in `settings.json`, `PanelResetSetting`: Immediately, 30 s, 1 min, 90 s by default, or Never). `PanelReset` (core) keeps the time the panel was hidden, on `ContinuousClock`, which runs through sleep. `AppDelegate.hidePanel`, the one path every hide takes, records it, and `showPanel` forgets it, so only hidden time counts. A path that shows the panel builds its screen inside `LauncherModel.resettingFirst`, which first resets to an empty root search if the hide was long enough (`PanelReset.enter`): the launcher hotkey and the menu bar item (`resetIfDue`), `openFromHotkey`, a user-initiated `launchCommand` view launch, and `showArguments`. The reset unloads the command on screen as Esc to root does, except a `launchCommand` caller, which `unloadReplaced` unloads after its call is answered. `presented()` never resets: it runs after the path has built its screen, and a reset there would throw the hotkey's or `launchCommand`'s target away. A command that closes the window with `popToRootType: Suspended` (`closeMainWindow`, `showHUD`) suspends the reset for that hide (`PanelReset.suspend`). The launcher hotkey doesn't hide the panel while a `confirm` sheet is on it.
    - `LauncherModel` holds the panel's state. Root search ranks `ApplicationIndex`, installed commands and Fudge's own items (`RootSearch.builtInItems`: "Fudge Settings", "Create Quicklink", "Reload Extensions" and "Quit Fudge", so nothing needs the menu bar) with `RootSearch` (fuzzy match, then `LaunchHistory`). "Reload Extensions" runs the menu bar item's own reload (`reloadAll`, set by `AppDelegate`). "Quit Fudge" asks through `confirm` first, and it's never recorded in `LaunchHistory` (`RootItem.recordsLaunch`), so an empty search never offers it first. Commands run through `ExtensionHost`, and its messages update the screen.
    - **Aliases and Enabled** come from `settings.json` too (`CommandSettings.alias`/`enabled`, `ExtensionSettings.enabled`). `LauncherModel.applySettings()` rebuilds root search from the cached installed extensions with `RootSearch.applying`, which drops disabled commands and sets aliases; it runs on every reload and whenever the Settings window changes something. An exact alias (case-insensitive) outranks everything (`exactAliasScore`), and `RootSearch.rows` puts it above the calculator card: that's the one row order the panel draws and ↑↓ follows. An alias prefix ranks next. For a command with arguments, "alias, space, rest" in the search field selects it and moves the rest into its first argument field (`CommandAliases.handOff`). `CommandAliases.problem` holds the alias rules (1–32 characters, no whitespace, unique ignoring case). A disabled command's hotkey isn't registered (`FudgeSettings.availableHotkeys`), and `CommandLocator` refuses `launchCommand` for it (`LaunchCommandError.disabled`).
    - **Arguments.** A selected command's `arguments` get fields after the query, which then shrinks to its text. `ArgumentInput` (core) holds what's entered and which field has the keyboard, and takes the keys: Tab and ⇧Tab between the fields, Esc back to the query, ⌫ in an empty field back one, ↑↓ on a dropdown argument. ↵ with a required argument empty moves the keyboard there and outlines it. A launch passes every argument in `launchProps.arguments`, with an empty string for those left empty, and the fields start over. They also start over when the selection moves, but not when a launch couldn't start.
    - **Quicklinks** (FUD-86) are root items too (`RootItem.quicklink`, kind "Quicklink"), from `QuicklinkStore` (core): `quicklinks.json`, `{ "quicklinks": [ { id, name, link, application?, createdAt } ] }`, read tolerantly and written atomically, keeping keys it doesn't know on the file and on each entry, and entries that aren't valid quicklinks (no `id`, a `name` outside 1–64 characters, no `link`). It never overwrites a file it can't read (`Unreadable`). `applySettings` reads it again, so a change shows at once. Search matches the name, and the link without its placeholders like a subtitle (`secondaryText`, `QuicklinkTemplate.searchableText`), so typing "argument" doesn't list every quicklink with a field. `QuicklinkTemplate` (core) reads the link's placeholders: arguments (`{argument name="…" default="…" options="a, b"}`, an unnamed `{argument}`, and Raycast's older bare `{Query}`; the same name twice is one field, at most 3), which become root search's argument fields (`fields`: a dropdown for `options`, required unless there's a default), dynamic values (`{clipboard}`, `{uuid}`, `{date}`, `{time}`, `{datetime}`, in the Mac's format and calendar), and modifiers (`raw`, `percent-encode`, `uppercase`, `lowercase`, `trim`) after a `|` outside quotes, so `default="a|b"` stays one attribute. Raycast's other dynamic names (`{selection}`, `{day}`, `{cursor}`, `{browser-tab}`, `{snippet}`), attributes Fudge doesn't know and unbalanced braces are a `problem` naming the placeholder; such a quicklink shows, with no fields, and opening it shows the problem. Dynamic names ignore letter case (`{Date}`). In a URL every value is encoded as JavaScript's `encodeURIComponent` does, unless it's `raw`; in a path (starting with `/` or `~`) values go in as they are; a link that is one placeholder is taken raw. The clipboard is read only for a link that uses `{clipboard}` (`usesClipboard`), and reads as nothing when it's marked concealed or transient (`clipboardText`). ↵ fills it in, and `QuicklinkOpening` (core) checks the result: a URL with a scheme, or a path that exists. It opens through `SystemCalls`' `open`, with the quicklink's `application` (a bundle id) or the default app, then records the launch and hides the panel; any failure is a toast (`SystemCalls.message(of:)`: Fudge's message or the system's localized one) and the panel stays. The row's icon is the opening app's: the `application`'s, else the default app for the scheme, else the path's own icon; nothing is fetched. ⌘K adds Copy Link (⇧⌘C, the link as saved), Edit Quicklink… (⌘E) and Delete Quicklink… (⌃X, after `confirm`).
    - **The Create Quicklink form** makes and edits quicklinks: the "Create Quicklink" root item, Edit Quicklink…, and an extension's `Action.CreateQuicklink`. It's a Form view built in core (`QuicklinkForm.view`: Name, Link with its info text, and Open With, a dropdown of "Default" then root search's applications by bundle id; an app it names that isn't listed is kept, by its bundle id), shown as a `CommandScreen` whose session is `QuicklinkForm.session`, so `FormScreen`, ⌘↵, ⌘K, Tab and Esc work as in any Form. Nothing of it reaches the host: `send` hands its events to `quicklinkFormEvent`, and drops its `pop` and `unload`. Its fields are uncontrolled with fixed node ids, so a render keeps what was typed. ⌘↵ (Save Quicklink) reads the file again and checks `QuicklinkDraft.problems` (core): a name of 1–64 characters that no other quicklink has, ignoring case and spaces around it, and a link with no placeholder problem that's a URL with a scheme, a path (`/`, `~` or `~/`), or starts with a placeholder (`{clipboard}`). Problems show as the fields' `error`s, each until its field is edited. Saving trims both, replaces the edited quicklink by `id` (keeping its `createdAt` and keys Fudge doesn't know) or adds a new one, writes the file (an `Unreadable` one stays as it is, with a toast), shows the HUD "Quicklink saved" and closes the form. Closing (a save, or Esc) goes back to root search, with its query cleared after a save, or to the extension's view it was opened over (`QuicklinkFormState.returnTo`). That view's session keeps running meanwhile: its renders, errors and exit wait in `deferred` and are handled once it's back, and its calls are answered as usual. If the form goes any other way (a launch, Pop to Root Search, a reset), `quicklinkFormLeft` unloads that session too.
    - **`Action.CreateQuicklink`** renders a host `Action` with `fudgeBuiltIn: "createQuicklink"` and a `quicklink` prop (its link, name and application: a name or bundle id, or an `Application`'s name, path and bundle id; the icon isn't used). `ActionPanelReader` makes it `ActionTarget.createQuicklink(QuicklinkRequest)`, and running it opens the form over the command's view, filled in by `QuicklinkDraft(request:commandTitle:applications:)`: the link, the name or else the command's title, and the application matched by bundle id, path or name, ignoring case (else Default).
    - **The calculator.** On each root query, `Calculator.evaluate` (core) tries `TimeZoneConversion` (`13.00 copenhagen time to new york time`, `3pm cet in pst`, `time in tokyo`), then `CurrencyConversion` (`100 usd to eur`, `€100 in usd`, `100 € in kr`: the ECB's codes from a static list, four symbols, and `kr` as the locale's krone or krona, else DKK), then `UnitConversion` (`13kg to lbs`, through Foundation's `Measurement`, with exact factors where Foundation rounds), then `Arithmetic` (a recursive-descent parser with `%`, `!`, functions and implicit products, where a sign binds looser than a right-associative `^`, so `-2^2` is -4). It ignores queries over 200 characters, a lone number, constants alone (`e`, `pi pi`), an ISO date (`2026-11-20`), and non-finite results. Numbers are read and written in a `NumberFormat` (core): the `numberFormat` setting, "Same as macOS" by default, resolved from `Locale.current` for each query (`NumberFormatSetting.resolve`), so `Calculator.evaluate` takes a format besides the locale, which still names times, dates and currencies. Reading (`NumberFormat.number`): the decimal separator starts the fraction, at most once, and the format's grouping separator (`typedGrouping`: `.`, `,`, or `'` and `’` alike) is dropped wherever it stands between two digits, with no group sizes checked, since it's only there for the eye (`0.1234` is 1234 and `1.5` is 15 with "1.234,5"). A grouping separator anywhere else (`.5`, `5.`, `1..2` there), or a second decimal separator, means no card. The tokenizer and the conversions' patterns keep every grouping character inside a number (`NumberFormat.groupingCharacters`) and let the format decide. A grouping the locale writes as a space is shown on the card but never read, since a space separates tokens. Copies use the decimal separator without grouping. A number can have an exponent with no spaces inside (`1e-7`, `2.5E3`, `2e+1`, and the card's own `1.152921505E18`), which conversions read too; without a digit straight after the `e` and its sign, the `e` is the constant (`2e`, `2e + 1`). The `CalculatorResult` shows as a card above the results: the question and answer, and a label under each. The card's answer has 10 significant digits, or, while it's written out (below 1e15), as many as its integer part has, up to 15, so it never rounds the integer part; a copied answer has up to 15, so floating-point noise (`0.1+0.2`) rounds away. A zone's label is its familiar abbreviation where `TimeZoneConversion.named` has one (`Copenhagen, CET`), else Foundation's offset (`GMT+8`). The card is selected first, and ↵ copies the answer (`RootActions.calculatorSections`, plus Copy Question and Answer ⌘⇧C) and closes the panel with a HUD. `now` and the time zone are parameters, so tests fix them.
    - **Currency rates** come from the European Central Bank, and only while `currencyRates` is on in `settings.json` (off by default; the General page's switch). `ExchangeRateUpdater` (core) loads `exchange-rates.json` and downloads when `ExchangeRatePolicy` says so: on turning it on, when the rates are a day old, at most once per 12 hours, one download at a time, keeping the old rates when one fails. ↵ on the "Couldn't download exchange rates" card retries at once. `ExchangeRates` parses the ECB's XML and says how fresh the rates are, under the card's arrow. The app's `ECBRatesFetcher` uses an ephemeral `URLSession` (no cookies, credentials or cache; 15 s; 1 MB), and `ExchangeRateSchedule` checks every hour. With the setting off, a currency query still gets a card ("Currency conversion is off"), and its ↵ opens Settings on the General page. When the rates change (they arrive, a download starts or fails), a currency card is evaluated again for the open query, keeping the selection (`Calculator.afterRatesChange`), with a command open too, so the card is right when the user comes back to root search. Snapshots never download.
    - `LauncherView` is the SwiftUI side.
    - **Lists and Grids.** `ListContent` (core) reads a `List` or `Grid` node: its sections and items, Raycast's own filtering (title and keywords, best match first, sections reordered unless `keepSectionOrder`), when the empty view shows (never while loading with an empty search), accessories with dates written relatively, and the search bar's `SearchBarDropdown`. A new search text filters the items read at the last render again (`ListContent.search`) rather than reading the view again. An item's `actions` and `detail` may come after the item (`ItemSlots`, `Item.deferred`): `LauncherModel` asks for those of the selected item and the ones around it (`requestSlots`, after every render and selection change, and before `onSelectionChange` is sent) and keeps them until the next render. `SlotRequests` (core) decides when: since a render carries in full exactly the items of the last request, each request names the whole window (8 before the selected item, 10 after, the selected one included), and a new one goes out when the selection nears the window's edge or an item near it is still held back with no answer coming. Meanwhile, ↵, ⌘↵ and ⌘K pressed before the selected item's have come wait for them, as does any shortcut of that item's actions (`Item.waitsForActions`), since the render names them. `HeldKey` (core) holds one such key: another replaces it and starts its time over; Esc, typing, the panel hiding (`panelHidden`) and leaving the view or command drop it, saying nothing; and one whose actions haven't come 2 s after the press is dropped with a failure toast, never run late. `LauncherModel` keeps the selection on the same item across renders, follows `selectedItemId`, reports `onSelectionChange`, keeps a search text per navigation level, and holds the dropdown's value (stored in `dropdown-values.json` for `storeValue`; `onChange` fires with the first value, as in Raycast). The dropdown opens as a panel (click or ⌘P) with its own search field, filtered by Fudge or by the extension's `onSearchTextChange`. A `searchText` the extension sets replaces the search field's text, except for stale echoes of typing (`FieldValue`). An item's `quickLook` (`{ path, name? }`) is read into a `QuickLookItem` (core): an absolute path, a `~/` path or a `file://` URL, titled by `name` or the file's name; anything else is none. With `pagination`, items coming into view or being selected near the end call `onLoadMore`, once for each length of the list. `ListScreen.swift` draws it all, with the detail pane for `isShowingDetail`. **A Grid is the same `ListContent`** (`layout: .grid`), so all of that applies to it unchanged. Each section carries a `GridSectionLayout` (core): the Grid's `columns` (clamped to 1–8 before it becomes an `Int`, `NaN` counting as not set; default 5, or the old `itemSize`), `aspectRatio`, `fit` and `inset` (in points, scaled with the column count), with the section's own overrides. A Grid item's `content` is a `GridItemContent`: an image, or a color drawn exactly as given. Its `drawing` says how: a picture (an asset, a file path, an http(s) image) follows the section's `fit`; an icon (a `fileIcon`, one of Raycast's icons, an emoji) is always drawn whole, centred inside the inset, so Fill never crops it; a color fills the cell. An image's mask shapes the drawn image, not the cell. `GridNavigation` (core) moves the selection in two dimensions, across sections to the nearest column, and decides when ← and → move it rather than the search field's cursor: with the field empty, or with the cursor at its end and nothing selected, and never with ⇧, ⌥, ⌘ or ⌃ (`fieldModifiers`; the `fn` and `numpad` flags every arrow key carries don't count). ↑↓ always do. While an input method is composing (marked text), no arrow moves a selection, in a Grid, a List or root search: they're the input method's. `GridScreen.swift` draws the cells, and paging asks for more two rows from the end.
    - **Markdown, metadata, images and colors** are shared by the views. `Markdown` (core) splits markdown into blocks, and `MarkdownView` draws them, with inline markdown through `AttributedString`. Code blocks wrap to the pane (inside over-long tokens too, with whitespace kept); tables scroll sideways, fading at the right edge while columns are hidden there. `MetadataEntry` (core) reads a `Metadata` node for `MetadataView`. `ExtensionImages` resolves an `Image.ImageLike` (file icons, assets with their `@dark` variant, file paths, Raycast's icons, emoji). `RaycastIcons` (core) maps every Raycast icon to an SF Symbol; a test checks that each icon in the generated enums has one and that each symbol exists. `ExtensionColor` (core) reads a `Color.ColorLike`: Raycast's named colors, any HTML color, or a light/dark pair.
    - **Remote images.** An `https://` image source, in an `Image.ImageLike` or in markdown, goes through `RemoteImages` (app), an observable entry per source so only the views showing that image redraw when it arrives, and its decoding; `RemoteImageStore` (core) keeps the entries, at most 300 in memory, and starts their loads. The placeholder shows meanwhile; a failure shows `fallback`, else the placeholder. The logic is in core: `RemoteImageURL` decides what's fetched (https only, no user info, no localhost, `.local`, one-label names or non-public IP literals, in every form `getaddrinfo` reads), `RemoteImageLoader` fetches (coalesced, 6 at once, 10 MB cut off while streaming, redirects re-checked) and says why a load failed (`RemoteImageFailure`), `RemoteImageCache` keeps bodies in `image-cache/` by the URL's SHA-256 with a sidecar (fresh for 24 h, then shown and revalidated with `If-None-Match`/`If-Modified-Since`, 200 MB, least recently used first), and `RemoteImageDecoder` refuses a header over 16,384 px and decodes thumbnails of at most 2048 px, or SVG up to 1 MB. `URLSessionImageFetcher` is the one `URLSession`: no cookies, credentials or URL cache, and authentication challenges cancelled. Markdown images honour `raycast-width`, `raycast-height` and `raycast-tint-color` (`MarkdownImageHints`). **Loading again** happens only when a view asks for the source, never on a timer, as `RemoteImageRetry` (core) decides: a network error, HTTP 408, 429 or 5xx is retried after 1 min, 5 min, 30 min, then every 2 h, or after a 429's or 503's `Retry-After` when that's longer, up to 2 h, with the fallback shown meanwhile; any other failure is final for the run. An image fetched 24 h ago or more is refreshed: a 304 keeps it without decoding again, a new body replaces it once decoded, and a failed refresh keeps it for another 24 h. One whose first load comes from the disk cache that old is shown at once and refreshed straight away, not at the next ask. Nothing starts while a load for that source runs. A source that leaves memory in back-off, or failed for good, keeps that (`RemoteImageRetries`, at most 1,000, oldest out): asked for again, it shows the fallback and loads only when it's due.
    - **Detail and Form** have no search field: their navigation title takes its place, and `handleKey` takes ↵ and Esc. `DetailScreen` shows the markdown with the metadata in a column beside it. `FormContent` (core) reads a Form's fields for `FormScreen`, and its `searchBarAccessory` when that's a `Form.LinkAccessory` with a text and a target (`LinkAccessory`): the title bar shows it at the right as a link (`ViewTitle`), mouse-only as in Raycast, truncating before the title and never wider than 40% of the bar, and a click opens the target as `Action.OpenInBrowser` does, then hides the panel. Over the link the pointer is a pointing hand, pushed and popped through `PointerPush` (core, by `LinkPointer`): popped on the way out, on the click, and when the panel hides with the pointer resting on it (`hidePanel`), and never more than it was pushed. A `Form.LinkAccessory` among the fields is skipped. `FieldValue` (core) holds what the user types, telling a controlled field's stale echoes from values the extension set itself. Each edit goes to the field's `onChange`. A `Form.Dropdown` reads like a search bar dropdown (`SearchBarDropdown`), and a `Form.TagPicker`'s tokens are kept by `TagPicking` (core). A `Form.DatePicker` shows its date, with a `DateTime`'s time beside it to edit in place, and a clear button (or ⌫). Space, ↵ or a click opens its calendar under the field: `DateCalendar` (core) highlights the field's day or today, ←→↑↓ and ⇞⇟ move it within `min` and `max`, and nothing is picked until ↵, Space or a click on a day picks one. The field keeps the keyboard, so `handleKey` gives the open calendar its keys first, Esc closes it before anything else, and any other key closes it and does what it always does. `FormDates` (core) makes a `Date` picker's value local midnight and a `DateTime` picker's whole minutes (limits with seconds clamp to whole minutes within them), within `min` and `max`, and `null` when cleared. A `Form.FilePicker` lists its paths with a × each, and Select… opens an `NSOpenPanel` as a sheet on the launcher (`FilePicking`, core, keeps the paths). The open panel only takes typing while Fudge is the active app, so Fudge activates for it, and `hidePanel` gives the keyboard back to the app that had it. The Dropdown and TagPicker both open the dropdown panel under the field: the panel has a source (`DropdownPanelSource`: the List's search bar, a Form dropdown or a TagPicker), and `FormFieldBounds` tells `LauncherView` where the field is. A field with `storeValue` (never a PasswordField) starts on the value saved when its form was last submitted (`FormValueStore`: `form-values/<extension>.json`, by command and field `id`), ahead of `defaultValue`. A Dropdown's or TagPicker's stored value waits for the field's items when they arrive after the first render, unless the field is changed first (`FormContent.Field.start`). When a field starts on something the extension's Form didn't register, such as a stored value or a dropdown's first item, the app reports it with `onChange`. `onFocus` and `onBlur` fire with Raycast's `FormEvent` when the keyboard moves from one field to another.
    - **Actions.** `ActionPanelReader` (core) turns an `ActionPanel` node into sections of `ActionEntry`. ↵ runs the first entry and ⌘↵ the second; in a Form, where ↵ belongs to the fields, ⌘↵ and ⌘⇧↵. ⌘K opens the action panel overlay, with search, sections and submenus (opening one calls its `onOpen`). An `Action.PickDate` (an `Action` with a `pickDate` prop and an `onChange`, `ActionEntry.pickDate`) opens a picker there in place of the list, as a submenu does; run with ↵, ⌘↵ or its shortcut, the overlay opens straight to it. `DatePick` (core) holds it: Form.DatePicker's calendar (`DateCalendar`, drawn by the shared `MonthView`) and a `DateTime`'s time, which Tab moves to. ↵, Space or a click on a day picks and calls `onChange` once with `FormDates`' value, ⌫ calls it with null, and Esc goes back to the list it came from, or closes the overlay, calling nothing. Closing the overlay any other way calls nothing either. The picker's keys come through `handleKey` with no field holding the keyboard (a Form's field lets go of it while the picker is open, and takes it back when the overlay closes), so typing filters nothing; a render keeps it open with the action's new title and limits (`DatePick.following`), or closes it when the action is gone. No Form field takes the keyboard while an overlay holds it, the action panel (picker or not) or a dropdown's panel, even when the fields change or the panel is shown again; the overlay's closing gives it to the last field, or the first if that's gone (`KeyboardFocus.formFieldAfterFieldsChange`, `formFieldAfterOverlay`). In root search the same overlay shows Fudge's own actions for the selected item, from `RootActions` (core): Open (↵) on everything, Configure Extension (⌘⇧,) on a command, Show in Finder (⌘⇧F) on an application. Their shortcuts work without opening the panel. An entry's `target` says what it runs: an extension's `Action` node (`onAction` in the running command), a `RootAction`, or `toggleQuickLook`, which the app performs itself (an `Action` with `fudgeBuiltIn: "toggleQuickLook"`, `ActionPanelReader.builtInProp`). An `NSEvent` local monitor in `AppDelegate` turns key presses into `KeyShortcut`s for `LauncherModel.handleKey` (⌘K, ⌘↵, actions' shortcuts) before the search field sees them. The key is named by what it types with no modifier at all (`characters(byApplyingModifiers: [])`), so ⌘⇧, is `,` with cmd and shift, not `<`. It leaves every key alone while an input method is composing (marked text), so ↑↓, Esc and ↵ reach the input method.
    - **Quick Look** (`Action.ToggleQuickLook`, however it's run) previews the selected item's `quickLook` file in macOS's Quick Look panel. `QuickLookState` (core) decides what it shows: a toggle opens it, or closes it if open, and an item without `quickLook` or whose file doesn't exist gets a failure toast instead; while it's open it follows the selection, and closes for an item without one, another view (a push, a pop, another command, root search), Esc, the launcher hiding (`hidePanel`), or its own close button. That button is noticed through `windowWillClose`, and also before every decision (a toggle, Esc, the selection moving): `QuickLookState.reconcile(panelVisible:)` closes the state when the panel isn't on screen, so ↓ never reopens a preview the user closed and one ⌘Y opens it. `QuickLookPreview` mirrors it into `QLPreviewPanel`: the app delegate is the panel's controller, which the responder chain reaches whether or not Fudge is active, and the panel is ordered front just above the launcher, with the launcher's Spaces and full-screen behaviour, without becoming key and without activating Fudge, so the keyboard stays with the launcher. If the user clicks the preview, `LauncherResign` (core) keeps the launcher open and gives it the keyboard back instead of hiding it, and `hidePanel` later returns the keyboard to the app the user was in when the preview opened (set at the click whatever `frontmostApplication` says yet, and forgotten when the panel hides); keys the preview gets meanwhile go where the launcher would send them: its shortcuts and a date picker's keys through `handleKey`, the arrows to the action panel, the dropdown's panel or the List or Grid (`PreviewArrow`, ←→ in a Grid as `GridNavigation` allows), and Esc. Snapshot runs and tests never touch Quick Look.

- **The extension host lives in `runtime/`.** It's written in TypeScript. Tests run the `.ts` files directly through Node's type stripping, and esbuild bundles `src/host.ts` and `src/worker.ts` into `runtime/dist/` as ES modules, with production React.
  - **The protocol.** The app talks to `host.ts` over stdin/stdout, one JSON message per line, as typed and parsed in `src/protocol.ts`. The app reads lines with `LineSplitter`, which looks at each byte once, and decodes them through `JSONSerialization` (`HostMessage(line:)`), falling back to `JSONDecoder`: a 1,000-row list is a line of several hundred kilobytes. Messages about a running command carry the `session` id the app chose when launching it. stdout carries nothing but the protocol: in the host, `console.log` goes to stderr, and a worker's output arrives as `log` messages.
  - **One worker thread per launch.** `worker.ts` intercepts `Module._load` so that `require("@raycast/api" | "react" | "react/jsx-runtime" | "react/jsx-dev-runtime")` gets the host's own modules. The extension and the renderer must share one React, or hooks break. The command is the module's default export; an old module that exports nothing and calls the deprecated `render(<Command />)` while it loads gets that element as its root instead (`recordRender` in `src/api/render.ts` keeps the first call during the load; any other call does nothing). The app shows nothing a no-view command renders, so a no-view command that does this fails with an error saying so. An old no-view module with neither does its work in its top-level code, which runs as it loads; its worker ends when that work does (the message port keeps it alive only while a call into the app waits for its answer, `holdWhilePending` in `bridge.ts`), and the host reports `finished`. A view or menu-bar module with neither has nothing to run.
  - **The renderer** (`src/renderer/`) is a React 19 host config. Host instances are plain objects named after the component (`List.Item`, `ActionPanel.Section`, …). Commits are coalesced into one snapshot per event-loop turn, and only the top navigation view (a `$view` instance) is sent. A `menu-bar` command renders the same way, its `MenuBarExtra` being the view.
  - **A no-view command's exit.** Before the worker reports `exit`, it waits until the host has read everything the command wrote to stdout and stderr (`flushOutput`, at most a second), so the last `console.log` arrives before the `exit` and the host stopping the worker can't lose it.
  - **Events.** The worker answers every `event` with one `eventSettled`, once the handler has returned (or its promise settled) and the render it caused has been sent (`Root.whenRendered`). The menu bar unloads a command only when every event has settled.
  - **Snapshot encoding.** Functions are sent as `{ "$fn": path }`, and the app calls one back with the node id and that path. Dates are sent as `{ "$date": iso }`. Element props (`actions`, `detail`, …) are rendered as `$slot` children and sent as nodes inside props. A `List.Item`'s or `Grid.Item`'s `actions` and `detail` are sent only for the first item, the one the view's `selectedItemId` names (read in each snapshot, one item only), and the items the app last asked for with `slots` (`Deferral` in `src/renderer/serialize.ts`); the others carry `{ "$deferred": true }`, and the worker answers `slots` with them, with an entry for every id asked for (`Root.slots`). A deferred `actions` also names the shortcuts its panel's actions use, as an index (`"shortcuts": 0`) into the view's `$shortcutSets`, where each distinct set appears once.
  - **Built-in actions** (`src/api/actions.ts`: CopyToClipboard, CreateQuicklink, Open, OpenInBrowser, OpenWith, Paste, PickDate, ShowInFinder, Trash, SubmitForm) are JS components over the host `Action`, doing their work through the system APIs. Paste is titled after the frontmost app ("Paste to TextEdit") once it's known, and shows a failed paste as a toast. ToggleQuickLook and CreateQuicklink (with its `quicklink`) render a host `Action` with `fudgeBuiltIn` and no `onAction`, for the app to perform; a CreateQuicklink without a link only shows a failure toast when picked. A background call only checks (`isTrusted(prompt: false)`), with no prompt and no offer, and leaves both for the next user-initiated refusal. Then `isTrusted()` calls the app's `AccessibilitySettingsOffer`, which shows Fudge's own alert (`AccessibilitySettingsAlert`, core) with a button that opens the Accessibility pane. It's a sheet on the panel when the panel is up, and it's shown on a later main-actor turn, so the refused call is answered first, with its usual message.
    - Everything that waits on another app runs off the main thread.
  - **The launch context.** `src/api/launch.ts` holds what the app sent with the launch: preferences, `LaunchEnvironment` (built by `LaunchEnvironment.make`) and launch props. `environment` reads it through getters. Raycast's deprecated `preferences` record (`src/api/deprecated.ts`) is built from it when first read: the declarations in the installed extension's `package.json` (beside `dist/`; the extension's, then the command's, which win), each with its resolved value. `createApiModule` leaves its members alone (`plainRecords`). The deprecated `randomId` is nanoid's: 21 URL-safe characters from `crypto.getRandomValues`. `LocalStorage` (one JSON file) and `Cache` (one `cache.json` per namespace, least recently used dropped beyond its capacity) read and write in the worker, under the paths the environment names in Fudge's support folder.
- **The Extension Store** is an extension bundled with Fudge, in `runtime/store-extension/` (`fudge-extension-store`), written against `@raycast/api` like any other. `npm run typecheck` checks it with its own `tsconfig.json`, and `runtime/test/store.test.ts` tests its modules, with a fake git runner and a local bare repository (no network).
  - `git.ts` keeps a shallow, blobless, sparse clone of github.com/raycast/extensions in its support folder's `repo/`, with only `/extensions/*/package.json` checked out. A README or an extension's source comes on demand through `sparse-checkout add`. The copy is refreshed when it's a day old or on ⌘R: the default branch's name (checked by `isValidBranch`) is fetched as `refs/heads/<branch>` into its remote-tracking ref, the branch moves there, every other ref and the reflogs go, and only what the refs reach is packed again, into one pack marked as the remote's, before `git prune`. So the copy stays one commit deep and `.git/shallow` names only that commit. `gc` can't do this in a blobless clone: it keeps every object that came from the remote, reachable or not, and its repack asks the remote for the old commits `.git/shallow` still names. Every git call is an argument array with a timeout (`timeouts.ts`: the long one for anything that downloads or rewrites the copy), and runs with `GIT_TERMINAL_PROMPT=0` and without the user's git configuration (`storeEnvironment`), so an `insteadOf` rule can't redirect it. Git isn't run until `xcode-select -p` succeeds, so macOS's offer to install the Command Line Tools never shows. Unloading the store ends its running git (`stopRunningGit`, in the command's effect cleanup, which `unload` runs), and turning the store off unloads its sessions and waits for them to exit (`LauncherModel.unloadSessions(ofExtension:)`) before Part A deletes `repo/`. A copy that can't be read, such as a clone stopped halfway, is deleted and cloned again. A failure before the list has ever loaded, which can only be the clone, shows in the load-error view, whose Refresh (↵, ⌘R) opens the copy again the same way and then refreshes it. A refresh runs only once the list has loaded from the copy, so a failed one, a default branch name `isValidBranch` refuses included, shows as a toast over the list, which stays usable.
  - **Files from the copy are read as regular files only** (`files.ts`, `readRegularFile`: opened with `O_NOFOLLOW` and `O_NONBLOCK`, then `fstat`), each kind with a size cap: every `package.json` for the list, a README, and the package-source check's `package.json` and lockfiles. git checks out a committed link as a link, so `README.md -> /dev/zero` would otherwise read forever.
  - `catalog.ts` keys each row by its manifest `name`. The name must pass the name rule and equal its folder's name before it's used in a path, a sparse pattern or `installed.json`.
  - `sources.ts` refuses an extension that could get packages from anywhere but registry.npmjs.org: an `.npmrc` anywhere in it, a lockfile entry off the registry (both lockfile shapes; `link`, and a `file:`, path, `user/repo` or tarball version too), an entry's own dependency specs that aren't registry versions (its dependency sections, or a version 1 entry's `requires`), or a dependency spec or override that isn't a registry version (a tarball name like `x.tgz` isn't). File names are compared ignoring case, as APFS and the build's copy by name do, and two names that differ only by case are refused.
  - `readme.ts` shows images only from GitHub's hosts; other images become their alt text. `detailMarkdown` lists each command with its mode (view, no-view, menu bar) and runs everything in the detail pane through it, the manifest's own text included. A source the renderer would read differently (whitespace, `<`, `>`, `)`) is refused, and a last pass (`rendererPass`) applies the renderer's own image rule to the finished text.
  - `store.ts` installs with `$FUDGE_CLI build <source> --into $FUDGE_EXTENSIONS_DIR`. Every git operation (refresh, a README's `sparse-checkout add`, install, uninstall) waits its turn in one queue (`oneAtATime`), so none overlaps another. Before asking, it runs `$FUDGE_CLI scan <source> --json`, and the confirmation says what it found (`compatibilityLine`): everything supported, up to five missing APIs and how many more, the categories of APIs Fudge leaves out on purpose, named apart ("It also uses AI, which Fudge leaves out."), or that the scan couldn't run, which doesn't stop the install. It records the folder's git tree id in `installed.json` ("Update available" when the id changes), and uninstalls only what it recorded. **Unloading the store doesn't stop a `fudge build` it started** (or npm under it), unlike its git: the worker's timeout goes with it, so the build runs to the end, or until npm's own network timeouts give up. That's acceptable because nothing is installed half-way: the build writes into a staging folder and swaps it in only at the end, and the extensions watcher picks the result up like any install. The store just doesn't record it, so it counts as installed another way.
- **`fudge build <folder>` installs an extension** (`ExtensionBuilder` in `FudgeCore`).
  - It reads `package.json` (`ExtensionManifest`) and compiles every command's `src/<name>.{tsx,ts,jsx,js}` with esbuild into `<extensions>/<name>/dist/<name>.cjs`. The modules the host provides (`ExtensionBuilder.providedModules`) stay external.
  - It writes the build into `.staging-<name>-<uuid>` with `package.json` and `assets/` alongside, then swaps the whole folder into place (a previous install is moved to `.old-<name>-<uuid>` first, then deleted).
  - It never writes into the source folder. When the source has no `node_modules`, it installs the dependencies into a temporary folder (`npm ci --ignore-scripts`; under `$TMPDIR` when it's set, which Foundation's `temporaryDirectory` ignores) and points esbuild at it with `NODE_PATH`.
  - **Ending the tool ends what it started.** `fudge build` and `fudge scan` run every program (esbuild, npm, node) through `ChildProcesses` (core): `posix_spawn` in a process group of its own, with default signals and only stdin, stdout and stderr passed on. On SIGTERM, SIGINT or SIGHUP the tool signals each child's whole group, so npm's and node's own children go too, waits up to a second, kills what's left, deletes `fudge build`'s staging and scratch folders, which `defer` would miss (`ChildProcesses.deleteOnSignal`; not a staging folder already being moved into place), and exits with 128 + the signal (`ChildProcesses.endChildrenOnSignals`). That's what makes the Extension Store's timeouts, which send SIGTERM, end the whole job.
  - Extensions live in `FudgePaths.extensionsDirectory`: `~/Library/Application Support/fudge/extensions`, or under `$FUDGE_SUPPORT_DIR`.
  - **The running app picks it up.** `ExtensionsWatcher` (core) watches the extensions folder through FSEvents, with file-level events. A path counts unless its first component under the folder starts with `.` (`.staging-*`, `.old-*`, `.DS_Store`), and a trailing 0.3 s debounce makes each install, rebuild or removal one reload: `LauncherModel.reloadExtensions()` (the installed extensions only, keeping the scanned applications, the query and the selection), the command hotkeys, and the Settings window if it's open. The menu's Reload Extensions also scans applications again. Snapshot runs don't watch.
- **The Makefile assembles the app bundle** (`make app`):
  - the `FudgeApp` binary becomes `Contents/MacOS/Fudge`
  - the `fudge` tool and esbuild's native binary go into `Contents/Helpers/`, where `ExtensionBuilder.locateEsbuild` finds esbuild next to the tool
  - `App/Info.plist` gets the version from `git describe`
  - `App/AppIcon.icon` (an Icon Composer icon) is compiled by `actool` into `Assets.car` and an `AppIcon.icns` fallback. That needs Xcode 26 or later.
  - the host and worker bundles go into `Contents/Resources/runtime/`, with `fudge scan`'s `compat-scan.js` and Raycast's types beside it (`raycast-api.d.ts`, with its MIT notice as `raycast-api.LICENSE`)
  - the helpers and the bundle are signed with `SIGN_IDENTITY`. From what `security find-identity -v -p codesigning` lists, the default is "fudge local signing", else the first `Apple Development:` identity, else ad hoc (see the README). It's picked by SHA-1, since two certificates can share a name. The `→ built` line names the identity, and with one, codesign's errors show and fail the build.
- **`make compat-scan DIR=<folder>` measures store compatibility statically** (`runtime/scripts/compat-scan.ts`). Every folder in `DIR` with a `package.json` and a `src/` is an extension, as in a checkout of raycast/extensions. Nothing is built or run.
  - `scripts/compat/scan.ts` turns each source file into JavaScript with esbuild, which drops type-only uses. Sources are read as regular files of at most 5 MB (`scripts/compat/files.ts`, as the store's `files.ts` does); a link, FIFO, device, folder or bigger file with a source's name is listed as unreadable, and nothing is followed. Tests and mocks are skipped (`*.test.*`, `*.spec.*`, and `__mocks__/`, `__tests__/`, `test/` and `tests/` folders). It collects the API paths used through `@raycast/api` imports (`Clipboard.copy`, `Action.CopyToClipboard`) and the names imported from `@raycast/utils`.
  - Each path is checked against `createApiModule()`. A stub anywhere on the path makes it `missing`, a lowercase member's included. So do the markers in `src/api/stubs.ts`: `UNAVAILABLE` is on the actions that render but fail when picked (`render-but-fail`), `NOT_DRAWN` is on the components the app can't draw yet, listed at the end of `components.ts` (`not-drawn`), and `LEFT_OUT` is on `OAuth`, which is there but left out by design, so it and everything under it still count as `missing`. Whoever teaches the app to draw one removes it from that list in the same PR. Anything under a record of the extension's own data (`plainRecords`, the deprecated `preferences`, read as `preferences.apiKey.value`) is `implemented`, since its members are the extension's own names.
  - A path Raycast's types don't declare (`Color.Gray`, a mock's `showToast.mockResolvedValue`) is `not-raycast`: listed, but not a gap. `raycastDeclarations` (`scripts/raycast-types.ts`) reads the vendored types for that.
  - `@raycast/utils` is bundled from each extension's own dependencies, so its calls are invisible. `scripts/compat/raycast-utils.generated.ts` maps each of its exports to the API paths it needs, and an extension using one inherits them (`via @raycast/utils`). `scripts/compat/raycast-utils.ts` generates it from the `src/` files in the source map of the pinned `@raycast/utils` devDependency, with the same path extraction. `npm run generate` rewrites it, and `npm run typecheck` fails while it's stale.
  - One extension's scan is `scanExtension` (`scripts/compat/extension.ts`), shared with **`fudge scan <folder> [--json]`**. The CLI runs `scripts/compat/fudge-scan.ts`, bundled by `npm run build` into `dist/compat-scan.js` and shipped in the app, with node (`CompatScanner`, core). The app has esbuild's binary but not its JS package, so the bundle marks `esbuild` external, `toJavaScript` takes the transform to use (esbuild's JS API is imported only when it's the default), and the CLI passes `FUDGE_ESBUILD` (the binary, `binaryTransform`) and `FUDGE_RAYCAST_TYPES`: the types beside the script, unless it's set already or there are none there, as with `FUDGE_COMPAT_SCAN=runtime/dist/compat-scan.js` in a checkout, which then reads the vendored ones. The JSON report (`report`) names the extension, says `supported` (no gaps and every file read), and lists each gap with its kind and by-design category. The text output (`describe`) lists what Fudge doesn't have yet, then each by-design category apart. Before scanning it checks that the esbuild it was given runs (exit 1 with one line if not, rather than every file unreadable), and a folder without a `package.json` file and a `src` folder, or with either as a link, is refused with exit 2. `FudgeToolTests` runs the real `fudge` binary end to end.
  - The Markdown report counts extensions with no gaps, those lacking only APIs left out by design (AI, Browser Extension, and OAuth per decision D-50), and the rest. It ranks gaps by API and kind. `--json <file>` also writes each extension's gaps with their kind.
- **`runtime/vendor/raycast-api/index.d.ts` is Raycast's own type definitions** (MIT, notice alongside). It's the contract Fudge implements. `make raycast-types` copies it unmodified from the `@raycast/api` release named by `RAYCAST_API_VERSION`. Never edit it by hand.

## Gotchas

- **Names must differ by more than case.** macOS file systems are case-insensitive, so no two products or targets may differ only by case. The tool's product is `fudge`, which is why the app's product is `FudgeApp`.
- **Scripts that also run as a command guard it by their own file name** (`import.meta.url.endsWith(".ts")`), as `raycast-types.ts` and `raycast-utils.ts` do. Bundled into another script, `import.meta.url` and `process.argv[1]` are both the bundle's, so a guard on those alone would run the generator from inside `compat-scan.js`.
- **Proxies must return frozen properties untouched.** `createApiModule` wraps components to name missing members, but it leaves frozen constants (`Keyboard`, enums) unwrapped, or JavaScript throws.
- **Runtime TypeScript must be erasable syntax only** (`erasableSyntaxOnly`), because tests run it through type stripping. That rules out enums, namespaces, parameter properties and JSX in `.ts` files. Relative imports carry the `.ts` extension.
- **Compiled extension commands are CommonJS.** The worker loads them with `require`, which is the only way `Module._load` can hand them Fudge's modules.
- **actool's paths must be absolute.** `xcrun actool` hands the work to a shared daemon, which resolves relative paths against its own working directory. That's whichever checkout started it, so with several worktrees, relative paths make one worktree's `make app` write the icon into another's `build/`. actool can also exit 0 when it compiled nothing, and it reports errors on stdout, so `make app` checks for `Assets.car` and then shows `build/actool.log`.
- **Apps opened from Finder don't get the shell's `PATH`.** That's why `Runtime.locateNode` checks `$FUDGE_NODE`, `Contents/Helpers`, Homebrew and `/usr/local` before `PATH`.
- **SwiftUI's `TextField` writes its unchanged text back** now and then, three times on ↵ before `onSubmit` and again when it loses the keyboard. Setters bound to a field must ignore writes that change nothing, or they'll redo work such as resetting the selection.
- **`.onAppear` runs once for the panel's lifetime**, not each time it's shown. Showing the panel (`LauncherModel.presented()`) and clicking a row ask for the keyboard back explicitly (`keyboardRequests`). `KeyboardFocus` (core) names the field each screen wants, and the views move it there through `nil`, because setting a `@FocusState` to the value it already holds does nothing, even when AppKit's first responder has moved.
- **Check the panel's layout without showing it:** `build/Fudge.app/Contents/MacOS/Fudge --snapshot out.png [--query text] [--activate]`. It renders the panel off-screen and transparent, then saves a PNG and quits. A snapshot run never activates (activation policy `.prohibited`, set in `main.swift` before launch), its windows refuse key status (`LauncherPanel.refusesKey`, `SettingsNSWindow`), and it installs no status item (Fudge's or a menu-bar command's), global hotkey or key monitor, so it can't take anyone's typing or put a second icon in the menu bar. Just before saving, it prints `snapshot-state active=… appActive=… key=… canBecomeKey=…` to stderr; all four are false. In the command `--activate` opened, `--search text` types into its search field, `--dropdown value` picks a search bar dropdown value, `--actions` opens the action panel, `--pick-date <title>` opens the picker of the `Action.PickDate` with that title (from the list with `--actions`, else straight), `--run-action <title>`, given once or more, runs those actions in order, half a second apart (e.g. an extension's Create Quicklink, then Save Quicklink), and `--open-dropdown` opens the dropdown's panel (in a Form, its first Dropdown's; `--open-tags`, its first TagPicker's; `--open-date`, its first DatePicker's calendar). `--settings` renders the Settings window instead (`--settings :permissions` its Permissions page, `:quicklinks` its Quicklinks page), `--onboarding [<step>]` the onboarding window, and `--accessibility allowed|missing` and `--login-item <status>` fix what Accessibility and Open at Login show, so nothing asks the system. The window blur doesn't render in snapshots. Run snapshots one at a time: several at once can miss their timing. `make run` opens the app with `open -n`, because LaunchServices would otherwise hand the open to a live snapshot run (same bundle id) and fail with -600; just before, it checks again that none of the user's own Fudge is running.
- **Permission grants need a signing identity.** macOS ties Accessibility and Automation grants to the app's designated requirement. An ad hoc signature's is its cdhash, which changes with every build, so each ad hoc `make run` drops them; builds signed with an identity keep them. **The first signing with an identity shows a keychain prompt** that only a person can answer (Always Allow). Until someone has, `make app` waits on it, so build with `SIGN_IDENTITY=-` where nobody has. CI and releases have no identity and stay ad hoc. No certificate, key, name or team ID ever goes into the repo.
- **The local-network check reads the URL, not DNS.** A public name that resolves to a private address isn't caught. https mostly covers it, since a LAN device rarely has a certificate for a public name.
- **AppKit draws nothing inside an SVG `<a>` element**, so `RemoteImageDecoder.svgForDrawing` unwraps links before `NSImage(data:)` sees the SVG.
- **Tests must not touch the user's system.** Never trash, open, copy, read the selection, post key events or send Apple Events for real in a test, and smoke-run extensions with a throwaway `HOME`: commands do what they say.
- **Swift tests that build extensions need esbuild** from `runtime/node_modules`. `make test` installs it; without it, `swift test` skips those tests.
- **npm may block install scripts.** esbuild works without its postinstall step, so don't approve it just to silence the warning.

## Conventions

- Swift for the app and the tool. TypeScript only in `runtime/`, because extensions are JavaScript.
- Docs describe what exists. No roadmaps, status tables or TODO lists in committed files.
- Every setting has a control in the Settings window. `settings.json` and the other support files are never the documented way to change one.
- An on/off setting shown as a row in the Settings window is a switch on the right, with its label (and any explanation) on the left, as in System Settings. A column of on/off cells in a table, like the Commands page's Enabled, uses checkboxes, as do extensions' own Forms.
- Conventional commits (`feat:`, `fix:`, `chore:`, `docs:`), scoped by area where it helps, e.g. `feat(runtime): ...`, `feat(app): ...`, `feat(cli): ...`.
- `AGPL-3.0-or-later` everywhere. Files taken from MIT-licensed upstream keep their notice next to them. New dependencies must be AGPL-compatible.
- Third-party GitHub Actions are pinned to commit SHAs, with the version in a trailing comment.
- **A probe or hand check that launches a second Fudge** which creates status items, windows or preferences runs from a copy of the bundle with a **different bundle id**, e.g. `plutil -replace CFBundleIdentifier -string io.github.jakeobsen.fudge.probe <copy>/Contents/Info.plist`. Builds with the same bundle id share the real app's preferences, whatever `HOME` or `FUDGE_SUPPORT_DIR` says, and that's how a probe once hid the user's menu bar icon. `--snapshot` runs are exempt: they create no status item, take no keyboard and write no preferences.
- **Help text, in the app and the README, is brief and says what a feature does, for an end user.**
- **The product's name is Fudge**, capitalized, in all text people read. `fudge` is only the CLI command, paths, env variables and identifiers.

## CI and releases

- **CI** (`.github/workflows/ci.yml`) runs `make lint` and `make test` on pull requests and pushes to `mainline`. `swift test` compiles every target, so the app's code is checked, but the app bundle is not assembled.
- **The release workflow** (`.github/workflows/release.yml`) is the only place the app bundle gets built. It runs on a pushed `v*` tag: tests, then `make app CONFIG=release VERSION=<tag>`, then the bundle zipped with `ditto` and uploaded as a workflow artifact.
