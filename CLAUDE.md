# CLAUDE.md

Guidance for AI coding agents working in this repository. User-facing docs are in README.md.

## What this is

fudge is a keyboard launcher for macOS, built to run extensions written for Raycast's `@raycast/api` without changing them. It is a native Swift app. Extensions run in a separate Node.js process, the extension host.

## Architecture

- **One Swift package, three targets.**
  - `FudgeApp` is the app: an accessory app with a menu bar item and no Dock icon.
    - **Global hotkeys** go through Carbon (`CarbonHotKeys` in `HotKey.swift`), which needs no Accessibility permission: one event handler, one id per registration. `HotKeyRegistry` (core) decides what's registered: the launcher's hotkey (`hotkey` in `settings.json`, default ⌥Space) and each installed command's (`commands` in `settings.json`, by `<extension>/<command>`), registering only what changed. Hotkeys of commands that aren't installed stay in the file but aren't registered. `HotKeySpec` (core) is the text form (`option+s`, `f5`, `keycode:<n>` for keys with no name), and an F-key may stand alone. `FudgeSettings` reads `settings.json` tolerantly, and writes it atomically, keeping keys it doesn't know. A pressed command hotkey calls `LauncherModel.openFromHotkey`, which follows `HotKeyLaunch` (core): open it as root search would, hide the panel when it's the view command on screen, or show root search with the fields when a required argument is empty. A no-view command run by hotkey doesn't clear root search when it finishes (`LaunchOrigin`). Root-search rows show a command's hotkey as keycaps (`Keycaps`, labelled as the current keyboard layout types the key).
    - `LauncherPanel` is a non-activating `NSPanel`: it takes keys while the app you were in stays frontmost.
    - `LauncherModel` holds the panel's state. Root search ranks `ApplicationIndex`, installed commands and fudge's own items (`RootSearch.builtInItems`: "fudge Settings") with `RootSearch` (fuzzy match, then `LaunchHistory`). Commands run through `ExtensionHost`, and its messages update the screen.
    - **Arguments.** A selected command's `arguments` get fields after the query, which then shrinks to its text. `ArgumentInput` (core) holds what's entered and which field has the keyboard, and takes the keys: Tab and ⇧Tab between the fields, Esc back to the query, ⌫ in an empty field back one, ↑↓ on a dropdown argument. ↵ with a required argument empty moves the keyboard there and outlines it. A launch passes every argument in `launchProps.arguments`, with an empty string for those left empty, and the fields start over. They also start over when the selection moves, but not when a launch couldn't start.
    - **The calculator.** On each root query, `Calculator.evaluate` (core) tries `TimeZoneConversion` (`13.00 copenhagen time to new york time`, `3pm cet in pst`, `time in tokyo`), then `CurrencyConversion` (`100 usd to eur`, `€100 in usd`, `100 € in kr`: the ECB's codes from a static list, four symbols, and `kr` as the locale's krone or krona, else DKK), then `UnitConversion` (`13kg to lbs`, through Foundation's `Measurement`, with exact factors where Foundation rounds), then `Arithmetic` (a recursive-descent parser with `%`, `!`, functions and implicit products). It ignores queries over 200 characters, a lone number or constant, and non-finite results. Numbers are read and written in the locale: where the decimal separator is `.`, a `,` before three digits groups. The `CalculatorResult` shows as a card above the results: the question and answer, a label under each, and up to 10 significant digits. The card is selected first, and ↵ copies the answer (`RootActions.calculatorSections`, plus Copy Question and Answer ⌘⇧C) and closes the panel with a HUD. `now` and the time zone are parameters, so tests fix them.
    - **Currency rates** come from the European Central Bank, and only while `currencyRates` is on in `settings.json` (off by default; the General page's checkbox). `ExchangeRateUpdater` (core) loads `exchange-rates.json` and downloads when `ExchangeRatePolicy` says so: on turning it on, when the rates are a day old, at most once per 12 hours, one download at a time, keeping the old rates when one fails. ↵ on the "Couldn't download exchange rates" card retries at once. `ExchangeRates` parses the ECB's XML and says how fresh the rates are, under the card's arrow. The app's `ECBRatesFetcher` uses an ephemeral `URLSession` (no cookies, credentials or cache; 15 s; 1 MB), and `ExchangeRateSchedule` checks every hour. With the setting off, a currency query still gets a card ("Currency conversion is off"), and its ↵ opens Settings on the General page. Snapshots never download.
    - `LauncherView` is the SwiftUI side.
    - **Lists.** `ListContent` (core) reads a `List` node: its sections and items, Raycast's own filtering (title and keywords, best match first, sections reordered unless `keepSectionOrder`), when the empty view shows (never while loading with an empty search), accessories with dates written relatively, and the search bar's `SearchBarDropdown`. `LauncherModel` keeps the selection on the same item across renders, follows `selectedItemId`, reports `onSelectionChange`, keeps a search text per navigation level, and holds the dropdown's value (stored in `dropdown-values.json` for `storeValue`; `onChange` fires with the first value, as in Raycast). The dropdown opens as a panel (click or ⌘P) with its own search field, filtered by fudge or by the extension's `onSearchTextChange`. A `searchText` the extension sets replaces the search field's text, except for stale echoes of typing (`FieldValue`). With `pagination`, items coming into view or being selected near the end call `onLoadMore`, once for each length of the list. `ListScreen.swift` draws it all, with the detail pane for `isShowingDetail`.
    - **Markdown, metadata, images and colors** are shared by the views. `Markdown` (core) splits markdown into blocks, and `MarkdownView` draws them, with inline markdown through `AttributedString`. Code blocks wrap to the pane (inside over-long tokens too, with whitespace kept); tables scroll sideways, fading at the right edge while columns are hidden there. `MetadataEntry` (core) reads a `Metadata` node for `MetadataView`. `ExtensionImages` resolves an `Image.ImageLike` (file icons, assets with their `@dark` variant, file paths, Raycast's icons, emoji). `RaycastIcons` (core) maps every Raycast icon to an SF Symbol; a test checks that each icon in the generated enums has one and that each symbol exists. `ExtensionColor` (core) reads a `Color.ColorLike`: Raycast's named colors, any HTML color, or a light/dark pair. Remote images aren't loaded; they show a placeholder.
    - **Detail and Form** have no search field: their navigation title takes its place, and `handleKey` takes ↵ and Esc. `DetailScreen` shows the markdown with the metadata in a column beside it. `FormContent` (core) reads a Form's fields for `FormScreen`, and `FieldValue` (core) holds what the user types, telling a controlled field's stale echoes from values the extension set itself. Each edit goes to the field's `onChange`. A `Form.Dropdown` reads like a search bar dropdown (`SearchBarDropdown`), and a `Form.TagPicker`'s tokens are kept by `TagPicking` (core). A `Form.DatePicker` shows its date, with a `DateTime`'s time beside it to edit in place, and a clear button (or ⌫). Space, ↵ or a click opens its calendar under the field: `DateCalendar` (core) highlights the field's day or today, ←→↑↓ and ⇞⇟ move it within `min` and `max`, and nothing is picked until ↵, Space or a click on a day picks one. The field keeps the keyboard, so `handleKey` gives the open calendar its keys first, Esc closes it before anything else, and any other key closes it and does what it always does. `FormDates` (core) makes a `Date` picker's value local midnight and a `DateTime` picker's whole minutes (limits with seconds clamp to whole minutes within them), within `min` and `max`, and `null` when cleared. A `Form.FilePicker` lists its paths with a × each, and Select… opens an `NSOpenPanel` as a sheet on the launcher (`FilePicking`, core, keeps the paths). The open panel only takes typing while fudge is the active app, so fudge activates for it, and `hidePanel` gives the keyboard back to the app that had it. The Dropdown and TagPicker both open the dropdown panel under the field: the panel has a source (`DropdownPanelSource`: the List's search bar, a Form dropdown or a TagPicker), and `FormFieldBounds` tells `LauncherView` where the field is. A field with `storeValue` (never a PasswordField) starts on the value saved when its form was last submitted (`FormValueStore`: `form-values/<extension>.json`, by command and field `id`), ahead of `defaultValue`. A Dropdown's or TagPicker's stored value waits for the field's items when they arrive after the first render, unless the field is changed first (`FormContent.Field.start`). When a field starts on something the extension's Form didn't register, such as a stored value or a dropdown's first item, the app reports it with `onChange`. `onFocus` and `onBlur` fire with Raycast's `FormEvent` when the keyboard moves from one field to another.
    - **Actions.** `ActionPanelReader` (core) turns an `ActionPanel` node into sections of `ActionEntry`. ↵ runs the first entry and ⌘↵ the second; in a Form, where ↵ belongs to the fields, ⌘↵ and ⌘⇧↵. ⌘K opens the action panel overlay, with search, sections and submenus. In root search the same overlay shows fudge's own actions for the selected item, from `RootActions` (core): Open (↵) on everything, Configure Extension (⌘⇧,) on a command, Show in Finder (⌘⇧F) on an application. Their shortcuts work without opening the panel. An entry's `target` says what it runs: an extension's `Action` node (`onAction` in the running command) or a `RootAction`. An `NSEvent` local monitor in `AppDelegate` turns key presses into `KeyShortcut`s for `LauncherModel.handleKey` (⌘K, ⌘↵, actions' shortcuts) before the search field sees them. The key is named by what it types with no modifier at all (`characters(byApplyingModifiers: [])`), so ⌘⇧, is `,` with cmd and shift, not `<`. It leaves every key alone while an input method is composing (marked text), so ↑↓, Esc and ↵ reach the input method.
    - **The General page** (`GeneralPage.swift`) is the Settings window's first page, and the one ⌘, Settings… and "fudge Settings" open on: the launcher's hotkey (read-only) and the currency checkbox.
    - **The Commands page** (`CommandsPage.swift`) is the Settings window's second page: every installed extension, expanded to its commands, with each command's hotkey. Recording a hotkey suspends all of fudge's hotkeys (`HotKeyRegistry.suspend`), so pressing one records it instead of firing. Ending the recording (saving, Esc, or closing the window) resumes them. A conflict (`HotKeyConflict`: the launcher's key, another command's, or no ⌘ ⌥ ⌃) or a shortcut the system refuses keeps the old hotkey and shows why in the cell.
    - `SettingsWindow.swift` is the Settings window: each extension's preferences, stored by `PreferenceStore` in `preferences/<extension>.json`. Before a launch, `PreferenceResolver` merges stored values, manifest defaults and type defaults. It turns appPicker references into Raycast `Application` objects, and the launch message carries the values to `getPreferenceValues()`. A command with an unset required preference opens this window instead of running. The other ways in: Settings… (⌘,) in the menu bar item; ⌘, in the panel, and the "fudge Settings" root item, on the General page; ⌘⇧, (Configure Extension) on the extension of the command selected in root search or running. An extension's own action shortcut wins over ⌘, and ⌘⇧, inside its command. `openExtensionPreferences()` and `openCommandPreferences()` open it on the calling extension.
  - `FudgeCLI` is the `fudge` command-line tool.
  - `FudgeCore` is shared code, and the only target with tests.

  Put logic in `FudgeCore`, where it can be tested. Keep the app and the tool thin.
- **The extension host lives in `runtime/`.** It's written in TypeScript. Tests run the `.ts` files directly through Node's type stripping, and esbuild bundles `src/host.ts` and `src/worker.ts` into `runtime/dist/` as ES modules, with production React.
  - **The protocol.** The app talks to `host.ts` over stdin/stdout, one JSON message per line, as typed and parsed in `src/protocol.ts`. Messages about a running command carry the `session` id the app chose when launching it. stdout carries nothing but the protocol: in the host, `console.log` goes to stderr, and a worker's output arrives as `log` messages.
  - **One worker thread per launch.** `worker.ts` intercepts `Module._load` so that `require("@raycast/api" | "react" | "react/jsx-runtime" | "react/jsx-dev-runtime")` gets the host's own modules. The extension and the renderer must share one React, or hooks break.
  - **The renderer** (`src/renderer/`) is a React 19 host config. Host instances are plain objects named after the component (`List.Item`, `ActionPanel.Section`, …). Commits are coalesced into one snapshot per event-loop turn, and only the top navigation view (a `$view` instance) is sent.
  - **Snapshot encoding.** Functions are sent as `{ "$fn": path }`, and the app calls one back with the node id and that path. Dates are sent as `{ "$date": iso }`. Element props (`actions`, `detail`, …) are rendered as `$slot` children and sent as nodes inside props.
  - **Built-in actions** (`src/api/actions.ts`: CopyToClipboard, Open, OpenInBrowser, OpenWith, ShowInFinder, Trash, SubmitForm) are JS components over the host `Action`, doing their work through the system APIs. The ones fudge can't perform (Paste, CreateQuicklink, ToggleQuickLook, …) still render, and show a failure toast when picked. `Keyboard.Shortcut.Common` holds Raycast's documented combinations as `{ macOS, Windows }` pairs.
  - **Forms.** `Form` provides a registry (`src/api/form-state.ts`) where each mounted field keeps its value under its `id`: `value`, else `defaultValue` (read on mount), else the field's empty value. Fields always carry an `onChange`, which the app calls as the user edits, and `Action.SubmitForm` submits the registry. Fields with `storeValue` are marked in the registry, and `Action.SubmitForm` sends their values to the app (`form.storeValues`, Dates encoded as `$date`) before it calls `onSubmit`. `Form.DatePicker.isFullDay` and `Action.PickDate.isFullDay` are the same function (`src/api/dates.ts`). Entries belong to field instances, so a field remounted under a new `key` replaces the old one's value.
  - **`@raycast/api` is `src/api/`.** `index.ts` exports what's implemented. `module.ts` wraps it so that any other Raycast export is a stub that throws `NotAvailableError` naming the API (e.g. `Clipboard.copy isn't available in fudge yet`). `scripts/raycast-types.ts` derives two files from the vendored types: the list of Raycast's exports (`src/api/raycast-exports.generated.ts`) and its enums with their values (`src/api/raycast-enums.generated.ts`: `Icon`, `Color`, `Action.Style`, …). `make raycast-types` regenerates them after updating the types, or run `npm run generate` by hand. `npm run typecheck` fails while either is stale.
  - **Calls into the app** go through `src/bridge.ts` (`callApp(method, params)`), which sends an `rpc` message and waits for the app's `rpcResult`. On the Swift side, `SystemCalls` answers them (clipboard, `open`, Trash, Finder, applications, the selection). `LauncherModel` handles `preferences.*`, `command.launch`, `form.storeValues` and the window calls: toasts in the bottom bar, the HUD (`HUDWindow`), `alert.confirm` (an `NSAlert` sheet on the panel), `window.close`, `window.popToRoot` and `searchBar.clear`. A toast's actions come back through the `toastAction` message.
  - **`launchCommand`** (`src/api/launch-command.ts`) checks its options in the worker, makes the arguments strings, and encodes `context` with `encode` (`src/protocol.ts`): Dates as `{ "$date": iso }`, Buffers as `{ "$buffer": base64 }`. It then sends `command.launch`. In the app, `LaunchRequest` reads the call and `CommandLocator` (core) finds the command: in the caller's extension, or in the one with that name and owner (else author). It fills every manifest argument, and its checks turn away what can't run: menu-bar commands (in one place, `checkMode`), view commands in the background, and missing required arguments or preferences in the background. A user-initiated launch with a required argument empty shows root search with the command's fields instead; an unset required preference opens Settings. The first time an extension opens another extension's command, the user is asked through `confirm`, and `LaunchPermissions` keeps the answer in `launch-permissions.json`. The launch itself goes through `prepareLaunch` and `launch`, as from root search. A background launch is `quiet`: no status line, the panel stays as it is, failures show in the HUD, and it isn't recorded in `LaunchHistory`. The call is answered once the `launch` message is sent, and only then is a replaced command on screen unloaded. Swift carries `context` untouched, and the launched command's worker revives it into `launchProps.launchContext`.
  - **The selection.** `getSelectedText()` and `getSelectedFinderItems()` call `selection.text` and `selection.finderItems`; the logic is `SelectedText` and `FinderSelection` (core), and `FudgeApp/Selection.swift` is the system side, behind small protocols. Both read the frontmost app, which is the one the user was in because the panel doesn't activate fudge.
    - `SelectedText` asks the app's focused element for its selected text through the Accessibility API. When that gives nothing, it snapshots the pasteboard (every item, every type), posts ⌘C to the app (`CGEvent.postToPid` from a private event source, on the key that types "c" in the current layout), polls `changeCount` for up to 500 ms, and restores the snapshot before answering, without types over 50 MB, unless `changeCount` never moved (then nothing touched the pasteboard). A snapshot marked `org.nspasteboard.ConcealedType` (a password manager's copy) isn't written back: the pasteboard is left empty, because a restored password gets a new `changeCount` and the manager never auto-clears it. Fallbacks run one at a time. It never posts ⌘V or ⌘X. macOS's Accessibility prompt shows at most once per run.
    - `FinderSelection` asks for Automation permission first (`AEDeterminePermissionToAutomateTarget`, no timeout, since the user may be reading the consent dialog), then sends Finder `core/getd` of `selection` as an alias list with a 5 s timeout. It resolves POSIX paths in Finder's order, folders without a trailing slash.
    - Everything that waits on another app runs off the main thread.
  - **The launch context.** `src/api/launch.ts` holds what the app sent with the launch: preferences, `LaunchEnvironment` (built by `LaunchEnvironment.make`) and launch props. `environment` reads it through getters. `LocalStorage` (one JSON file) and `Cache` (one `cache.json` per namespace, least recently used dropped beyond its capacity) read and write in the worker, under the paths the environment names in fudge's support folder.
- **`fudge build <folder>` installs an extension** (`ExtensionBuilder` in `FudgeCore`).
  - It reads `package.json` (`ExtensionManifest`) and compiles every command's `src/<name>.{tsx,ts,jsx,js}` with esbuild into `<extensions>/<name>/dist/<name>.cjs`. The modules the host provides (`ExtensionBuilder.providedModules`) stay external.
  - It copies `package.json` and `assets/` alongside, then swaps the whole folder into place.
  - It never writes into the source folder. When the source has no `node_modules`, it installs the dependencies into a temporary folder (`npm ci --ignore-scripts`) and points esbuild at it with `NODE_PATH`.
  - Extensions live in `FudgePaths.extensionsDirectory`: `~/Library/Application Support/fudge/extensions`, or under `$FUDGE_SUPPORT_DIR`.
- **The Makefile assembles the app bundle** (`make app`):
  - the `FudgeApp` binary becomes `Contents/MacOS/Fudge`
  - the `fudge` tool and esbuild's native binary go into `Contents/Helpers/`, where `ExtensionBuilder.locateEsbuild` finds esbuild next to the tool
  - `App/Info.plist` gets the version from `git describe`
  - `App/AppIcon.icon` (an Icon Composer icon) is compiled by `actool` into `Assets.car` and an `AppIcon.icns` fallback. That needs Xcode 26 or later.
  - the host and worker bundles go into `Contents/Resources/runtime/`
  - the helpers and the bundle are signed with `SIGN_IDENTITY`. From what `security find-identity -v -p codesigning` lists, the default is "fudge local signing", else the first `Apple Development:` identity, else ad hoc (see the README). It's picked by SHA-1, since two certificates can share a name. The `→ built` line names the identity, and with one, codesign's errors show and fail the build.
- **`make compat-scan DIR=<folder>` measures store compatibility statically** (`runtime/scripts/compat-scan.ts`). Every folder in `DIR` with a `package.json` and a `src/` is an extension, as in a checkout of raycast/extensions. `scripts/compat/scan.ts` turns each source file into JavaScript with esbuild, which drops type-only uses. It then collects the API paths used through `@raycast/api` imports (`Clipboard.copy`, `Action.CopyToClipboard`) and checks each against `createApiModule()`. The Markdown report ranks the missing APIs by how many extensions use them; `--json <file>` also writes each extension's gaps. Nothing is built or run.
- **`runtime/vendor/raycast-api/index.d.ts` is Raycast's own type definitions** (MIT, notice alongside). It's the contract fudge implements. `make raycast-types` copies it unmodified from the `@raycast/api` release named by `RAYCAST_API_VERSION`. Never edit it by hand.

## Gotchas

- **Names must differ by more than case.** macOS file systems are case-insensitive, so no two products or targets may differ only by case. The tool's product is `fudge`, which is why the app's product is `FudgeApp`.
- **Proxies must return frozen properties untouched.** `createApiModule` wraps components to name missing members, but it leaves frozen constants (`Keyboard`, enums) unwrapped, or JavaScript throws.
- **Runtime TypeScript must be erasable syntax only** (`erasableSyntaxOnly`), because tests run it through type stripping. That rules out enums, namespaces, parameter properties and JSX in `.ts` files. Relative imports carry the `.ts` extension.
- **Compiled extension commands are CommonJS.** The worker loads them with `require`, which is the only way `Module._load` can hand them fudge's modules.
- **actool's paths must be absolute.** `xcrun actool` hands the work to a shared daemon, which resolves relative paths against its own working directory. That's whichever checkout started it, so with several worktrees, relative paths make one worktree's `make app` write the icon into another's `build/`. actool can also exit 0 when it compiled nothing, and it reports errors on stdout, so `make app` checks for `Assets.car` and then shows `build/actool.log`.
- **Apps opened from Finder don't get the shell's `PATH`.** That's why `Runtime.locateNode` checks `$FUDGE_NODE`, `Contents/Helpers`, Homebrew and `/usr/local` before `PATH`.
- **SwiftUI's `TextField` writes its unchanged text back** now and then, three times on ↵ before `onSubmit` and again when it loses the keyboard. Setters bound to a field must ignore writes that change nothing, or they'll redo work such as resetting the selection.
- **`.onAppear` runs once for the panel's lifetime**, not each time it's shown. Showing the panel (`LauncherModel.presented()`) and clicking a row ask for the keyboard back explicitly (`keyboardRequests`). `KeyboardFocus` (core) names the field each screen wants, and the views move it there through `nil`, because setting a `@FocusState` to the value it already holds does nothing, even when AppKit's first responder has moved.
- **Check the panel's layout without showing it:** `build/Fudge.app/Contents/MacOS/Fudge --snapshot out.png [--query text] [--activate]`. It renders the panel off-screen and transparent, then saves a PNG and quits. A snapshot run never activates (activation policy `.prohibited`, set in `main.swift` before launch), its windows refuse key status (`LauncherPanel.refusesKey`, `SettingsNSWindow`), and it installs no status item, global hotkey or key monitor, so it can't take anyone's typing or put a second icon in the menu bar. Just before saving, it prints `snapshot-state active=… appActive=… key=… canBecomeKey=…` to stderr; all four are false. In the command `--activate` opened, `--search text` types into its search field, `--dropdown value` picks a search bar dropdown value, `--actions` opens the action panel, and `--open-dropdown` opens the dropdown's panel (in a Form, its first Dropdown's; `--open-tags`, its first TagPicker's; `--open-date`, its first DatePicker's calendar). The window blur doesn't render in snapshots. Run snapshots one at a time: several at once can miss their timing.
- **Permission grants need a signing identity.** macOS ties Accessibility and Automation grants to the app's designated requirement. An ad hoc signature's is its cdhash, which changes with every build, so each ad hoc `make run` drops them; builds signed with an identity keep them. **The first signing with an identity shows a keychain prompt** that only a person can answer (Always Allow). Until someone has, `make app` waits on it, so build with `SIGN_IDENTITY=-` where nobody has. CI and releases have no identity and stay ad hoc. No certificate, key, name or team ID ever goes into the repo.
- **Tests must not touch the user's system.** Never trash, open, copy, read the selection, post key events or send Apple Events for real in a test, and smoke-run extensions with a throwaway `HOME`: commands do what they say.
- **Swift tests that build extensions need esbuild** from `runtime/node_modules`. `make test` installs it; without it, `swift test` skips those tests.
- **npm may block install scripts.** esbuild works without its postinstall step, so don't approve it just to silence the warning.

## Conventions

- Swift for the app and the tool. TypeScript only in `runtime/`, because extensions are JavaScript.
- Docs describe what exists. No roadmaps, status tables or TODO lists in committed files.
- Conventional commits (`feat:`, `fix:`, `chore:`, `docs:`), scoped by area where it helps, e.g. `feat(runtime): ...`, `feat(app): ...`, `feat(cli): ...`.
- `AGPL-3.0-or-later` everywhere. Files taken from MIT-licensed upstream keep their notice next to them. New dependencies must be AGPL-compatible.
- Third-party GitHub Actions are pinned to commit SHAs, with the version in a trailing comment.
- fudge makes no network connections of its own: no updater, telemetry or crash reporting. The one exception is opt-in: with currency conversion turned on, it downloads the ECB's daily exchange rates (`ECBRatesFetcher`).

## CI and releases

- **CI** (`.github/workflows/ci.yml`) runs `make lint` and `make test` on pull requests and pushes to `mainline`. `swift test` compiles every target, so the app's code is checked, but the app bundle is not assembled.
- **The release workflow** (`.github/workflows/release.yml`) is the only place the app bundle gets built. It runs on a pushed `v*` tag: tests, then `make app CONFIG=release VERSION=<tag>`, then the bundle zipped with `ditto` and uploaded as a workflow artifact.
