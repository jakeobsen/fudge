# CLAUDE.md

Guidance for AI coding agents working in this repository. User-facing docs are in README.md.

## What this is

fudge is a keyboard launcher for macOS, built to run extensions written for Raycast's `@raycast/api` without changing them. It is a native Swift app. Extensions run in a separate Node.js process, the extension host.

## Architecture

- **One Swift package, three targets.**
  - `FudgeApp` is the app: an accessory app with a menu bar item and no Dock icon. The item's glyph is `MenuBarIcon`, a fudge cube drawn in code as a template image. Its autosave name is `fudge` (`AppDelegate.statusItemName`), because macOS keeps whether a status item is shown in the app's preferences under that name, and an unnamed item's `Item-0` was once saved as hidden. It's shown at every launch, and its `behavior` is `[]`, so ⌘-dragging can't remove it.
    - **Global hotkeys** go through Carbon (`CarbonHotKeys` in `HotKey.swift`), which needs no Accessibility permission: one event handler, one id per registration. `HotKeyRegistry` (core) decides what's registered: the launcher's hotkey (`hotkey` in `settings.json`, default ⌥Space, read and written through `FudgeSettings.launcherHotkey`) and each installed command's (`commands` in `settings.json`, by `<extension>/<command>`), registering only what changed. A refused change of the launcher's hotkey registers the old one again (`setLauncher`); one refused at launch stays wanted, marked `launcherRefused`, and is tried again on every `resume`. `AppDelegate.launcherHotkeyChanged` shows the outcome on the General page and in the menu bar item's "Open fudge (…)" title. Hotkeys of commands that aren't installed stay in the file but aren't registered. `HotKeySpec` (core) is the text form (`option+s`, `f5`, `keycode:<n>` for keys with no name), and an F-key may stand alone. `FudgeSettings` reads `settings.json` tolerantly, and writes it atomically, keeping keys it doesn't know. A pressed command hotkey calls `LauncherModel.openFromHotkey`, which follows `HotKeyLaunch` (core): open it as root search would, hide the panel when it's the view command on screen, or show root search with the fields when a required argument is empty. A no-view command run by hotkey doesn't clear root search when it finishes (`LaunchOrigin`). Root-search rows show a command's hotkey as keycaps (`Keycaps`, labelled as the current keyboard layout types the key).
    - `LauncherPanel` is a non-activating `NSPanel`: it takes keys while the app you were in stays frontmost. It opens a little above the middle of the screen **Show fudge on** picks (`showOnScreen`, `PanelScreen.choose` in core): the mouse's (the default), the primary one, or the one holding most of the frontmost app's topmost window, read with `CGWindowListCopyWindowInfo`, which needs no permission for bounds. Its bounds are flipped to Cocoa coordinates first (`PanelScreen.cocoaFrame`), and with no such window it's the mouse's screen.
    - **Esc** follows `EscapeAction` (core) and **Escape Key Behavior** (`escapeBehavior`). An open dropdown or action panel closes first either way. "Navigate back or close window" (the default) pops a view, clears the search, leaves the command, then hides; "Close window and pop to root" hides at once and resets to root search as Pop to Root Search does. A Form keeps navigating back, since Esc is its own key there, and Esc in an argument field, an input method, a hotkey recording or an alert sheet never reaches `LauncherModel.escape()`.
    - **Pop to Root Search** (`resetAfterSeconds` in `settings.json`, `PanelResetSetting`: Immediately, 30 s, 1 min, 90 s by default, or Never). `PanelReset` (core) keeps the time the panel was hidden, on `ContinuousClock`, which runs through sleep. `AppDelegate.hidePanel`, the one path every hide takes, records it, and `showPanel` forgets it, so only hidden time counts. A path that shows the panel builds its screen inside `LauncherModel.resettingFirst`, which first resets to an empty root search if the hide was long enough (`PanelReset.enter`): the launcher hotkey and the menu bar item (`resetIfDue`), `openFromHotkey`, a user-initiated `launchCommand` view launch, and `showArguments`. The reset unloads the command on screen as Esc to root does, except a `launchCommand` caller, which `unloadReplaced` unloads after its call is answered. `presented()` never resets: it runs after the path has built its screen, and a reset there would throw the hotkey's or `launchCommand`'s target away. A command that closes the window with `popToRootType: Suspended` (`closeMainWindow`, `showHUD`) suspends the reset for that hide (`PanelReset.suspend`). The launcher hotkey doesn't hide the panel while a `confirm` sheet is on it.
    - `LauncherModel` holds the panel's state. Root search ranks `ApplicationIndex`, installed commands and fudge's own items (`RootSearch.builtInItems`: "fudge Settings", "Reload Extensions" and "Quit fudge", so nothing needs the menu bar) with `RootSearch` (fuzzy match, then `LaunchHistory`). "Reload Extensions" runs the menu bar item's own reload (`reloadAll`, set by `AppDelegate`). "Quit fudge" asks through `confirm` first, and it's never recorded in `LaunchHistory` (`RootItem.recordsLaunch`), so an empty search never offers it first. Commands run through `ExtensionHost`, and its messages update the screen.
    - **Aliases and Enabled** come from `settings.json` too (`CommandSettings.alias`/`enabled`, `ExtensionSettings.enabled`). `LauncherModel.applySettings()` rebuilds root search from the cached installed extensions with `RootSearch.applying`, which drops disabled commands and sets aliases; it runs on every reload and whenever the Settings window changes something. An exact alias (case-insensitive) outranks everything (`exactAliasScore`), and `RootSearch.rows` puts it above the calculator card: that's the one row order the panel draws and ↑↓ follows. An alias prefix ranks next. For a command with arguments, "alias, space, rest" in the search field selects it and moves the rest into its first argument field (`CommandAliases.handOff`). `CommandAliases.problem` holds the alias rules (1–32 characters, no whitespace, unique ignoring case). A disabled command's hotkey isn't registered (`FudgeSettings.availableHotkeys`), and `CommandLocator` refuses `launchCommand` for it (`LaunchCommandError.disabled`).
    - **Arguments.** A selected command's `arguments` get fields after the query, which then shrinks to its text. `ArgumentInput` (core) holds what's entered and which field has the keyboard, and takes the keys: Tab and ⇧Tab between the fields, Esc back to the query, ⌫ in an empty field back one, ↑↓ on a dropdown argument. ↵ with a required argument empty moves the keyboard there and outlines it. A launch passes every argument in `launchProps.arguments`, with an empty string for those left empty, and the fields start over. They also start over when the selection moves, but not when a launch couldn't start.
    - **The calculator.** On each root query, `Calculator.evaluate` (core) tries `TimeZoneConversion` (`13.00 copenhagen time to new york time`, `3pm cet in pst`, `time in tokyo`), then `CurrencyConversion` (`100 usd to eur`, `€100 in usd`, `100 € in kr`: the ECB's codes from a static list, four symbols, and `kr` as the locale's krone or krona, else DKK), then `UnitConversion` (`13kg to lbs`, through Foundation's `Measurement`, with exact factors where Foundation rounds), then `Arithmetic` (a recursive-descent parser with `%`, `!`, functions and implicit products, where a sign binds looser than a right-associative `^`, so `-2^2` is -4). It ignores queries over 200 characters, a lone number, constants alone (`e`, `pi pi`), an ISO date (`2026-11-20`), and non-finite results. Numbers are read and written in a `NumberFormat` (core): the `numberFormat` setting, "Same as macOS" by default, resolved from `Locale.current` for each query (`NumberFormatSetting.resolve`), so `Calculator.evaluate` takes a format besides the locale, which still names times, dates and currencies. Reading (`NumberFormat.number`): the decimal separator starts the fraction, at most once, and the format's grouping separator (`typedGrouping`: `.`, `,`, or `'` and `’` alike) is dropped wherever it stands between two digits, with no group sizes checked, since it's only there for the eye (`0.1234` is 1234 and `1.5` is 15 with "1.234,5"). A grouping separator anywhere else (`.5`, `5.`, `1..2` there), or a second decimal separator, means no card. The tokenizer and the conversions' patterns keep every grouping character inside a number (`NumberFormat.groupingCharacters`) and let the format decide. A grouping the locale writes as a space is shown on the card but never read, since a space separates tokens. Copies use the decimal separator without grouping. A number can have an exponent with no spaces inside (`1e-7`, `2.5E3`, `2e+1`, and the card's own `1.152921505E18`), which conversions read too; without a digit straight after the `e` and its sign, the `e` is the constant (`2e`, `2e + 1`). The `CalculatorResult` shows as a card above the results: the question and answer, and a label under each. The card's answer has 10 significant digits, or, while it's written out (below 1e15), as many as its integer part has, up to 15, so it never rounds the integer part; a copied answer has up to 15, so floating-point noise (`0.1+0.2`) rounds away. A zone's label is its familiar abbreviation where `TimeZoneConversion.named` has one (`Copenhagen, CET`), else Foundation's offset (`GMT+8`). The card is selected first, and ↵ copies the answer (`RootActions.calculatorSections`, plus Copy Question and Answer ⌘⇧C) and closes the panel with a HUD. `now` and the time zone are parameters, so tests fix them.
    - **Currency rates** come from the European Central Bank, and only while `currencyRates` is on in `settings.json` (off by default; the General page's switch). `ExchangeRateUpdater` (core) loads `exchange-rates.json` and downloads when `ExchangeRatePolicy` says so: on turning it on, when the rates are a day old, at most once per 12 hours, one download at a time, keeping the old rates when one fails. ↵ on the "Couldn't download exchange rates" card retries at once. `ExchangeRates` parses the ECB's XML and says how fresh the rates are, under the card's arrow. The app's `ECBRatesFetcher` uses an ephemeral `URLSession` (no cookies, credentials or cache; 15 s; 1 MB), and `ExchangeRateSchedule` checks every hour. With the setting off, a currency query still gets a card ("Currency conversion is off"), and its ↵ opens Settings on the General page. Snapshots never download.
    - `LauncherView` is the SwiftUI side.
    - **Lists and Grids.** `ListContent` (core) reads a `List` or `Grid` node: its sections and items, Raycast's own filtering (title and keywords, best match first, sections reordered unless `keepSectionOrder`), when the empty view shows (never while loading with an empty search), accessories with dates written relatively, and the search bar's `SearchBarDropdown`. A new search text filters the items read at the last render again (`ListContent.search`) rather than reading the view again. An item's `actions` and `detail` may come after the item (`ItemSlots`, `Item.deferred`): `LauncherModel` asks for those of the selected item and the ones around it (`requestSlots`, after every render and selection change) and keeps them until the next render, and ↵, ⌘↵ and ⌘K pressed before the selected item's have come wait for them. `LauncherModel` keeps the selection on the same item across renders, follows `selectedItemId`, reports `onSelectionChange`, keeps a search text per navigation level, and holds the dropdown's value (stored in `dropdown-values.json` for `storeValue`; `onChange` fires with the first value, as in Raycast). The dropdown opens as a panel (click or ⌘P) with its own search field, filtered by fudge or by the extension's `onSearchTextChange`. A `searchText` the extension sets replaces the search field's text, except for stale echoes of typing (`FieldValue`). With `pagination`, items coming into view or being selected near the end call `onLoadMore`, once for each length of the list. `ListScreen.swift` draws it all, with the detail pane for `isShowingDetail`. **A Grid is the same `ListContent`** (`layout: .grid`), so all of that applies to it unchanged. Each section carries a `GridSectionLayout` (core): the Grid's `columns` (clamped to 1–8 before it becomes an `Int`, `NaN` counting as not set; default 5, or the old `itemSize`), `aspectRatio`, `fit` and `inset` (in points, scaled with the column count), with the section's own overrides. A Grid item's `content` is a `GridItemContent`: an image, or a color drawn exactly as given. Its `drawing` says how: a picture (an asset, a file path, an http(s) image) follows the section's `fit`; an icon (a `fileIcon`, one of Raycast's icons, an emoji) is always drawn whole, centred inside the inset, so Fill never crops it; a color fills the cell. An image's mask shapes the drawn image, not the cell. `GridNavigation` (core) moves the selection in two dimensions, across sections to the nearest column, and decides when ← and → move it rather than the search field's cursor: with the field empty, or with the cursor at its end and nothing selected, and never with ⇧, ⌥, ⌘ or ⌃ (`fieldModifiers`; the `fn` and `numpad` flags every arrow key carries don't count). ↑↓ always do. While an input method is composing (marked text), no arrow moves a selection, in a Grid, a List or root search: they're the input method's. `GridScreen.swift` draws the cells, and paging asks for more two rows from the end.
    - **Markdown, metadata, images and colors** are shared by the views. `Markdown` (core) splits markdown into blocks, and `MarkdownView` draws them, with inline markdown through `AttributedString`. Code blocks wrap to the pane (inside over-long tokens too, with whitespace kept); tables scroll sideways, fading at the right edge while columns are hidden there. `MetadataEntry` (core) reads a `Metadata` node for `MetadataView`. `ExtensionImages` resolves an `Image.ImageLike` (file icons, assets with their `@dark` variant, file paths, Raycast's icons, emoji). `RaycastIcons` (core) maps every Raycast icon to an SF Symbol; a test checks that each icon in the generated enums has one and that each symbol exists. `ExtensionColor` (core) reads a `Color.ColorLike`: Raycast's named colors, any HTML color, or a light/dark pair.
    - **Remote images.** An `https://` image source, in an `Image.ImageLike` or in markdown, goes through `RemoteImages` (app), which keeps an observable entry per source so only the views showing that image redraw when it arrives. The placeholder shows meanwhile; a failure shows `fallback`, else the placeholder. The logic is in core: `RemoteImageURL` decides what's fetched (https only, no user info, no localhost, `.local`, one-label names or non-public IP literals, in every form `getaddrinfo` reads), `RemoteImageLoader` fetches (coalesced, 6 at once, 10 MB cut off while streaming, redirects re-checked), `RemoteImageCache` keeps bodies in `image-cache/` by the URL's SHA-256 with a sidecar (fresh for 24 h, then shown and revalidated with `If-None-Match`/`If-Modified-Since`, 200 MB, least recently used first), and `RemoteImageDecoder` refuses a header over 16,384 px and decodes thumbnails of at most 2048 px, or SVG up to 1 MB. `URLSessionImageFetcher` is the one `URLSession`: no cookies, credentials or URL cache, and authentication challenges cancelled. Markdown images honour `raycast-width`, `raycast-height` and `raycast-tint-color` (`MarkdownImageHints`).
    - **Detail and Form** have no search field: their navigation title takes its place, and `handleKey` takes ↵ and Esc. `DetailScreen` shows the markdown with the metadata in a column beside it. `FormContent` (core) reads a Form's fields for `FormScreen`, and `FieldValue` (core) holds what the user types, telling a controlled field's stale echoes from values the extension set itself. Each edit goes to the field's `onChange`. A `Form.Dropdown` reads like a search bar dropdown (`SearchBarDropdown`), and a `Form.TagPicker`'s tokens are kept by `TagPicking` (core). A `Form.DatePicker` shows its date, with a `DateTime`'s time beside it to edit in place, and a clear button (or ⌫). Space, ↵ or a click opens its calendar under the field: `DateCalendar` (core) highlights the field's day or today, ←→↑↓ and ⇞⇟ move it within `min` and `max`, and nothing is picked until ↵, Space or a click on a day picks one. The field keeps the keyboard, so `handleKey` gives the open calendar its keys first, Esc closes it before anything else, and any other key closes it and does what it always does. `FormDates` (core) makes a `Date` picker's value local midnight and a `DateTime` picker's whole minutes (limits with seconds clamp to whole minutes within them), within `min` and `max`, and `null` when cleared. A `Form.FilePicker` lists its paths with a × each, and Select… opens an `NSOpenPanel` as a sheet on the launcher (`FilePicking`, core, keeps the paths). The open panel only takes typing while fudge is the active app, so fudge activates for it, and `hidePanel` gives the keyboard back to the app that had it. The Dropdown and TagPicker both open the dropdown panel under the field: the panel has a source (`DropdownPanelSource`: the List's search bar, a Form dropdown or a TagPicker), and `FormFieldBounds` tells `LauncherView` where the field is. A field with `storeValue` (never a PasswordField) starts on the value saved when its form was last submitted (`FormValueStore`: `form-values/<extension>.json`, by command and field `id`), ahead of `defaultValue`. A Dropdown's or TagPicker's stored value waits for the field's items when they arrive after the first render, unless the field is changed first (`FormContent.Field.start`). When a field starts on something the extension's Form didn't register, such as a stored value or a dropdown's first item, the app reports it with `onChange`. `onFocus` and `onBlur` fire with Raycast's `FormEvent` when the keyboard moves from one field to another.
    - **Actions.** `ActionPanelReader` (core) turns an `ActionPanel` node into sections of `ActionEntry`. ↵ runs the first entry and ⌘↵ the second; in a Form, where ↵ belongs to the fields, ⌘↵ and ⌘⇧↵. ⌘K opens the action panel overlay, with search, sections and submenus; opening a submenu calls its `onOpen`. In root search the same overlay shows fudge's own actions for the selected item, from `RootActions` (core): Open (↵) on everything, Configure Extension (⌘⇧,) on a command, Show in Finder (⌘⇧F) on an application. Their shortcuts work without opening the panel. An entry's `target` says what it runs: an extension's `Action` node (`onAction` in the running command) or a `RootAction`. An `NSEvent` local monitor in `AppDelegate` turns key presses into `KeyShortcut`s for `LauncherModel.handleKey` (⌘K, ⌘↵, actions' shortcuts) before the search field sees them. The key is named by what it types with no modifier at all (`characters(byApplyingModifiers: [])`), so ⌘⇧, is `,` with cmd and shift, not `<`. It leaves every key alone while an input method is composing (marked text), so ↑↓, Esc and ↵ reach the input method.
    - **The General page** (`GeneralPage.swift`) is the Settings window's first page, and the one ⌘, Settings… and "fudge Settings" open on: Open at Login, the launcher's hotkey, Show fudge on, Pop to Root Search, Escape Key Behavior (all three `SettingsPopupRow`s), the currency switch, the calculator's Number format (Same as macOS, "1,234.5" or "1.234,5", saved through `change {}`; changing it re-evaluates the open query), Clear Search History…, and Import / Export. The launcher's hotkey is recorded like a command's, through the same `HotkeyRecordingPrompt`, but it can't be cleared: ⌫ and the Reset button set ⌥Space (`HotKeyRecording.launcherEdit`). A command's hotkey wins, so a launcher hotkey that equals one is refused, naming the command. It's registered before it's saved, and a refusal leaves both the registration and the file as they were. **Open at Login** goes through the `LoginItem` protocol (core): `SMAppServiceLoginItem` (`SMAppService.mainApp`) in the app, and a `FixedLoginItem` in snapshot runs, so they never register anything (`--login-item <status>` sets its status). The switch shows the system's real status (`LoginItemState`, core), read whenever the page appears or the window becomes key, so changes made in System Settings show; nothing is stored. `LoginItemState.change` registers or unregisters, then reads the status back, with any error to show. **Clear Search History…** confirms in a sheet, then `LauncherModel.clearHistory()` empties `LaunchHistory` and `history.json`.
    - **Import / Export** (`BackupSection.swift`, at the bottom of General) writes and reads a `.fudgebackup` (declared in `App/Info.plist`). `Backup` (core) collects the parts from the support folder: `settings.json` without `extensionStoreConsentAt`, `launch-permissions.json`, `history.json`, `dropdown-values.json`, `command-metadata.json`, and `preferences/`, `form-values/`, `local-storage/` and `extension-data/` per extension (never the Extension Store's data folder, which is its clone of the store), plus a `manifest.json` listing the installed extensions with their source (the Extension Store's `installed.json`, else local). It takes only regular files inside the support folder and never follows a link; extension data over 100 MB leaves out the biggest extensions'. `BackupArchive` (core) writes an Apple Archive encrypted with AppleEncryptedArchive's scrypt profile. Its `setPassword` takes only 20 to 256 bytes, so the archive gets the hex SHA-256 of `"fudge-backup-v1:" + password` (64 characters) and the user's minimum stays 8; scrypt still runs on every guess, and Apple's `aea` tool can't open the file with the typed password. **An imported backup is untrusted input:** `BackupArchive.read` refuses links, hard links and anything that isn't a regular file, more than 100,000 entries, a path over 1,024 bytes or a segment over 255, and data over 100 MB in an entry or 150 MB in all, path bytes included, counted while reading. Each path is checked as it's read (`Backup.part(of:)`: a path fudge doesn't write, an invalid extension name, the Extension Store's folder), and the manifest's format as soon as it's read; `Backup.contents` also refuses a duplicate and a `settings.json` or keyed file that isn't a JSON object. Apple Archive's decoder already refuses `..` and absolute paths. A plain file in this support folder's `backups/` is fudge's own before-import backup and is read without the size limits (`Backup.readLimits`). Nothing is written until all of it has passed. `Backup.apply` then saves the current state, unencrypted, to `backups/before-import-<time>.fudgebackup` (folder 0700, file 0600, the last 3 kept, always including the one just written), and replaces each part the backup holds: an extension's data folder whole, the keyed files extension by extension, `settings.json` keeping this Mac's `extensionStore` and `extensionStoreConsentAt`. A failed write puts back everything changed so far, trying every step; if one fails, the staging folder stays and the error names the before-import file. The app then reloads settings, hotkeys, history and root search (`AppDelegate.afterImport`).
    - **The Extension Store** (FUD-50) is an extension bundled with the app (`Contents/Resources/store-extension`, built by `make app` from `runtime/store-extension` when that exists). It's always installed (`InstalledExtension.all(paths:resources:)`, which reads only its manifest), and using it takes two steps. **Enabled**, on the Commands page, is off by default for the store alone (`FudgeSettings.isEnabled(extension:)`, which always writes the store's state), so until it's ticked the store isn't in root search, its hotkeys aren't registered and `launchCommand` can't reach it. An install that had the store switched on before counts as enabled until either is changed. **The switch** is the first row of the store's Settings page (`ExtensionStoreSwitch`): turning it on shows the consent sheet and writes `extensionStore` and the ISO 8601 `extensionStoreConsentAt`. `FudgeSettings.isExtensionStoreOn` needs both, so a hand-set `true` counts as off. `FudgeSettings.setExtensionStore` writes the store's Enabled down first, so the switch never changes it. Turning it off, after its own sheet, removes both keys and deletes only the store's `repo/` (`ExtensionStore.deleteRepository`), keeping its `installed.json`. **While it's off, the app never starts the store's code:** `LauncherModel.launch` checks `ExtensionStore.isOff` against `settings.json` first. A launch the user started shows "The Extension Store is off." instead, a `Failure` with a `Notice`, drawn like an empty view. Its one action, Open Extension Store Settings (↵, ⌘K or ⌘⇧,), opens the store's page. A background launch is refused with the same words. The extension host's environment carries `FUDGE_CLI` (the bundle's `fudge`) and `FUDGE_EXTENSIONS_DIR` to every worker, and the store installs with `fudge build <folder> --into "$FUDGE_EXTENSIONS_DIR"` (`BuildArguments`: an absolute path to a folder that exists).
    - **The Commands page** (`CommandsPage.swift`) is the Settings window's second page: every installed extension, expanded to its commands (menu-bar ones included), with each command's alias, hotkey and Enabled checkbox (an extension's row has its own checkbox). The bundled Extension Store is listed too, unticked until it's enabled. An alias is saved on ↵, and Esc puts the old one back. Recording a hotkey suspends all of fudge's hotkeys (`HotKeyRegistry.suspend`), so pressing one records it instead of firing. While recording, `HotkeyRecordingPrompt` turns each key press into a `HotKeyRecording` (core): Esc alone cancels, ⌫ or ⌦ alone clears, anything else is the new hotkey. Ending the recording (saving, Esc, or closing the window) resumes them. A conflict (`HotKeyConflict`: the launcher's key, another command's, or no ⌘ ⌥ ⌃) or a shortcut the system refuses keeps the old hotkey and shows why in the cell.
    - **Menu bar commands.** `MenuBarController` puts each active `menu-bar` command in the menu bar as one `NSStatusItem` with an `NSMenu`. Running one from root search (or its hotkey) activates it; running it again refreshes it and opens its menu. ⌘K on an active one offers Deactivate Menu Bar Item (`RootAction.deactivateMenuBarItem`). `MenuBarStore` (core) keeps the active commands in `menu-bar.json`, at most 50, pruned of commands that aren't installed. It keeps keys it doesn't know, and never overwrites a file it can't read (`Unreadable`): activating or deactivating then fails with a toast saying why. A disabled command, or one of a disabled extension, stays in it but leaves the menu bar and stops refreshing, and comes back when it's turned on again (`MenuBarStore.shown`; `LauncherModel.applySettings` hands the controller the settings). Each item's autosave name is `menubar:<extension>/<command>` (`MenuBarStore.autosaveName`), so it keeps its own position and never takes over another item's saved state, and it's made visible whenever it's put in the menu bar. `MenuBarContent` (core) reads the `MenuBarExtra` tree: items without `onAction` disabled, sections as a heading between separators, submenus, ⌥ alternates, and each item's position path. `MenuBarLifecycle` (core) decides loads and unloads: at most one instance per command; Background at fudge's start and on the manifest `interval` (`MenuBarInterval`, at least 10 s, a `.common`-mode timer), UserInitiated when the menu opens or root search runs it; a tick while loaded is skipped and a click just opens the menu; unloaded once it has rendered without `isLoading`, its menu is closed and every `onAction` has settled (`eventSettled`). The item keeps the last tree. A pick made in that tree before the new instance's first render waits, then goes to the item at the same position path with the same title, or is dropped. Waiting picks are dropped too once no instance is still to render (`MenuBarLifecycle.awaitsFirstRender`: it failed or exited first, or the host stopped), so a later launch never runs them. UserInitiated errors show in the HUD; Background ones are logged and add a disabled "⚠ Last refresh failed" until a later render. `LauncherModel` starts the controller's commands (`launchMenuBarCommand`) and routes their sessions' `render`, `error`, `eventSettled` and `exit` to it; their rpcs are answered like any command's.
    - **The Permissions page** (`PermissionsPage.swift`) comes after General: Accessibility's status (`AccessibilityStatus`, read without a prompt when it's shown and every second while it's on screen), its reason, and Open Accessibility Settings. That button asks for macOS's prompt on the first click and opens the pane on later ones, or at once when something in this run already asked for the prompt (`AccessibilityPermission.request`, `SystemAccessibility.promptShown`), so the prompt and the pane never stack. Below it, always shown, are the answers to "Allow <A> to open <B>'s commands?" (`LaunchPermissionsSection`, `LaunchPermissions.entries`), each changeable or forgotten, with the file read again before each change, a line saying none has asked yet when there are none, and the unreadable-file notice. Show Onboarding Again restarts onboarding from Welcome.
    - **Onboarding** (`OnboardingWindow.swift`) opens at every launch until it's complete, once the extensions have loaded; never in snapshot runs, tests or the CLI. `Onboarding` (core) keeps the answered step ids in `onboarding.json` and decides what to show (`pending`): the unanswered steps, in order, then Done. Once it has been completed, Welcome isn't shown again, and a step added later shows on its own, then Done, under "Something new to decide" (`hasSomethingNew`). **`OnboardingStep`'s cases are the one list of steps**: adding a step means adding its case and drawing it. The steps use General's own controls (`LauncherHotkeyControls`, `OpenAtLoginControls`, `CurrencyRatesToggle`, and the Permissions page's `AccessibilityControls`), so an answer takes effect at once. Welcome also has **Restore from a Backup…**, General's import flow with its own sheets on the onboarding window (`SettingsModel.onboardingBackup`); a backup never holds `onboarding.json`, so onboarding carries on after an import. A step is answered when it's left with Get Started, Continue or Not Now, and saved straight away, so closing the window keeps the answers so far. Leaving a step or closing the window ends a hotkey recording. ⌘W and ⌘Q close the window as they do Settings (`WindowShortcut`), without completing onboarding. Unlike `settings.json` and `launch-permissions.json`, a broken `onboarding.json` is read as nothing answered and replaced on the next save, since it holds nothing else.
    - `SettingsWindow.swift` is the Settings window, with a fixed 200 pt sidebar beside the page (a `List` with the sidebar material, not a `NavigationSplitView`, so there's no divider to drag and nothing to collapse). Every way in goes through `SettingsWindowController.show`, which deminiaturizes the window, moves it to the current Space, activates fudge with `activate(ignoringOtherApps:)` (`activateFromUserAction`; the plain `activate()` can be declined since macOS 14, leaving the window behind the app in front) and orders it front and key. It's for user-initiated entries only, never a background path. ⌘Q closes the window as ⌘W and its close button do (`SettingsNSWindow.performKeyEquivalent`, `WindowShortcut` in core), and fudge keeps running; while a hotkey is being recorded, the recorder takes ⌘Q like any other key. The sidebar lists the extensions with preferences, and the Extension Store, whose page starts with its switch (`InstalledExtension.settingsPages`), enabled or not. The window holds each extension's preferences, stored by `PreferenceStore` in `preferences/<extension>.json`. Before a launch, `PreferenceResolver` merges stored values, manifest defaults and type defaults. It turns appPicker references into Raycast `Application` objects, and the launch message carries the values to `getPreferenceValues()`. A command with an unset required preference opens this window instead of running. The other ways in: Settings… (⌘,) in the menu bar item; ⌘, in the panel, and the "fudge Settings" root item, on the General page; ⌘⇧, (Configure Extension) on the extension of the command selected in root search or running. An extension's own action shortcut wins over ⌘, and ⌘⇧, inside its command. `openExtensionPreferences()` and `openCommandPreferences()` open it on the calling extension.
  - `FudgeCLI` is the `fudge` command-line tool.
  - `FudgeCore` is shared code, and the only target with tests.

  Put logic in `FudgeCore`, where it can be tested. Keep the app and the tool thin.
- **The extension host lives in `runtime/`.** It's written in TypeScript. Tests run the `.ts` files directly through Node's type stripping, and esbuild bundles `src/host.ts` and `src/worker.ts` into `runtime/dist/` as ES modules, with production React.
  - **The protocol.** The app talks to `host.ts` over stdin/stdout, one JSON message per line, as typed and parsed in `src/protocol.ts`. The app reads lines with `LineSplitter`, which looks at each byte once, and decodes them through `JSONSerialization` (`HostMessage(line:)`), falling back to `JSONDecoder`: a 1,000-row list is a line of several hundred kilobytes. Messages about a running command carry the `session` id the app chose when launching it. stdout carries nothing but the protocol: in the host, `console.log` goes to stderr, and a worker's output arrives as `log` messages.
  - **One worker thread per launch.** `worker.ts` intercepts `Module._load` so that `require("@raycast/api" | "react" | "react/jsx-runtime" | "react/jsx-dev-runtime")` gets the host's own modules. The extension and the renderer must share one React, or hooks break.
  - **The renderer** (`src/renderer/`) is a React 19 host config. Host instances are plain objects named after the component (`List.Item`, `ActionPanel.Section`, …). Commits are coalesced into one snapshot per event-loop turn, and only the top navigation view (a `$view` instance) is sent. A `menu-bar` command renders the same way, its `MenuBarExtra` being the view.
  - **Events.** The worker answers every `event` with one `eventSettled`, once the handler has returned (or its promise settled) and the render it caused has been sent (`Root.whenRendered`). The menu bar unloads a command only when every event has settled.
  - **Snapshot encoding.** Functions are sent as `{ "$fn": path }`, and the app calls one back with the node id and that path. Dates are sent as `{ "$date": iso }`. Element props (`actions`, `detail`, …) are rendered as `$slot` children and sent as nodes inside props. A `List.Item`'s or `Grid.Item`'s `actions` and `detail` are sent only for the first item and the items the app last asked for with `slots` (`Deferral` in `src/renderer/serialize.ts`); the others carry `{ "$deferred": true }`, and the worker answers `slots` with them, with an entry for every id asked for (`Root.slots`).
  - **Built-in actions** (`src/api/actions.ts`: CopyToClipboard, Open, OpenInBrowser, OpenWith, Paste, ShowInFinder, Trash, SubmitForm) are JS components over the host `Action`, doing their work through the system APIs. Paste is titled after the frontmost app ("Paste to TextEdit") once it's known, and shows a failed paste as a toast. OpenWith looks up the applications that can open its path only when its submenu opens (`onOpen`), not once per row. The ones fudge can't perform (CreateQuicklink, ToggleQuickLook, …) still render, and show a failure toast when picked. `Keyboard.Shortcut.Common` holds Raycast's documented combinations as `{ macOS, Windows }` pairs.
  - **Forms.** `Form` provides a registry (`src/api/form-state.ts`) where each mounted field keeps its value under its `id`: `value`, else `defaultValue` (read on mount), else the field's empty value. Fields always carry an `onChange`, which the app calls as the user edits, and `Action.SubmitForm` submits the registry. Fields with `storeValue` are marked in the registry, and `Action.SubmitForm` sends their values to the app (`form.storeValues`, Dates encoded as `$date`) before it calls `onSubmit`. `Form.DatePicker.isFullDay` and `Action.PickDate.isFullDay` are the same function (`src/api/dates.ts`). Entries belong to field instances, so a field remounted under a new `key` replaces the old one's value.
  - **`@raycast/api` is `src/api/`.** `index.ts` exports what's implemented. `module.ts` wraps it so that any other Raycast export is a stub that throws `NotAvailableError` naming the API (e.g. `Clipboard.copy isn't available in fudge yet`). `scripts/raycast-types.ts` derives two files from the vendored types: the list of Raycast's exports (`src/api/raycast-exports.generated.ts`) and its enums with their values (`src/api/raycast-enums.generated.ts`: `Icon`, `Color`, `Action.Style`, …). `make raycast-types` regenerates them after updating the types, or run `npm run generate` by hand. `npm run typecheck` fails while either is stale.
  - **Calls into the app** go through `src/bridge.ts` (`callApp(method, params)`), which sends an `rpc` message and waits for the app's `rpcResult`. On the Swift side, `SystemCalls` answers them (clipboard, `open`, Trash, Finder, applications, the selection). `LauncherModel` handles `preferences.*`, `command.launch`, `command.updateMetadata`, `clipboard.paste` (it hides the panel), `form.storeValues` and the window calls: toasts in the bottom bar, the HUD (`HUDWindow`), `alert.confirm` (an `NSAlert` sheet on the panel), `window.close`, `window.popToRoot` and `searchBar.clear`. A toast's actions come back through the `toastAction` message.
  - **`updateCommandMetadata`** (`src/api/command-metadata.ts`) sends `command.updateMetadata` with the calling command's new root-search subtitle, or null to go back to the manifest's. `CommandMetadata` (core) keeps it in `command-metadata.json`, by `<extension>/<command>`, keeps keys it doesn't know, and drops the entries of commands that aren't installed when the file is loaded (never from an empty listing); the manifest is never touched. A command's root item shows that subtitle, else the manifest's `subtitle`, else its extension's title, and search matches the extension's title either way.
  - **`launchCommand`** (`src/api/launch-command.ts`) checks its options in the worker, makes the arguments strings, and encodes `context` with `encode` (`src/protocol.ts`): Dates as `{ "$date": iso }`, Buffers as `{ "$buffer": base64 }`. It then sends `command.launch`. In the app, `LaunchRequest` reads the call and `CommandLocator` (core) finds the command: in the caller's extension, or in the one with that name and owner (else author). It fills every manifest argument, and its checks turn away what can't run: view commands in the background, a menu-bar command in the background unless it's active (`checkMode`), and missing required arguments or preferences in the background. A menu-bar command goes to `MenuBarController`: Background refreshes it like an interval tick, and UserInitiated activates it if needed and refreshes it, without opening its menu. A user-initiated launch with a required argument empty shows root search with the command's fields instead; an unset required preference opens Settings. The first time an extension opens another extension's command, the user is asked through `confirm`, and `LaunchPermissions` keeps the answer in `launch-permissions.json`. It never overwrites a file it can't read (`Unreadable`), which the Permissions page then says. The launch itself goes through `prepareLaunch` and `launch`, as from root search. A background launch is `quiet`: no status line, the panel stays as it is, failures show in the HUD, and it isn't recorded in `LaunchHistory`. The call is answered once the `launch` message is sent, and only then is a replaced command on screen unloaded. Swift carries `context` untouched, and the launched command's worker revives it into `launchProps.launchContext`.
  - **The selection.** `getSelectedText()` and `getSelectedFinderItems()` call `selection.text` and `selection.finderItems`; the logic is `SelectedText` and `FinderSelection` (core), and `FudgeApp/Selection.swift` is the system side, behind small protocols. Both read the frontmost app, which is the one the user was in because the panel doesn't activate fudge.
    - `SelectedText` asks the app's focused element for its selected text through the Accessibility API. When that gives nothing, it snapshots the pasteboard (every item, every type), posts ⌘C to the app (`CGEvent.postToPid` from a private event source, on the key that types "c" in the current layout), polls `changeCount` for up to 500 ms, and restores the snapshot before answering, without types over 50 MB, unless `changeCount` never moved (then nothing touched the pasteboard). A snapshot marked `org.nspasteboard.ConcealedType` (a password manager's copy) isn't written back: the pasteboard is left empty, because a restored password gets a new `changeCount` and the manager never auto-clears it. Fallbacks run one at a time. It never posts ⌘V or ⌘X.
    - `FinderSelection` asks for Automation permission first (`AEDeterminePermissionToAutomateTarget`, no timeout, since the user may be reading the consent dialog), then sends Finder `core/getd` of `selection` as an alias list with a 5 s timeout. It resolves POSIX paths in Finder's order, folders without a trailing slash.
    - `Paste` (`Clipboard.paste`, `Action.Paste`, `clipboard.paste`) snapshots the pasteboard the same way, writes the content as `Clipboard.copy` does, marked `org.nspasteboard.TransientType` and `AutoGeneratedType`, hides the panel unless `closeMainWindow` is false, waiting a run-loop turn plus 50 ms after hiding it so key status is back with the target app, and posts ⌘V to the frontmost app on the key that types "v". About a second later it writes the snapshot back if `changeCount` is still its own; a concealed snapshot is cleared instead. Pastes run one at a time. A paste while a restore is pending keeps that restore's snapshot, unless the pasteboard has changed since fudge's last write. Without Accessibility permission the content stays on the pasteboard and the call rejects; it never pastes into fudge itself.
    - `AccessibilityGate` holds the Accessibility check for both, so macOS's prompt shows at most once per run. macOS shows that prompt only when fudge isn't in the Accessibility list, so an entry that's off or left by an older build's signature gets none. `check()` says so: the first refusal asks for the prompt, and the next one, from either feature, also says `offerSettings`, once per run. Then `isTrusted()` calls the app's `AccessibilitySettingsOffer`, which shows fudge's own alert (`AccessibilitySettingsAlert`, core) with a button that opens the Accessibility pane. It's a sheet on the panel when the panel is up, and it's shown on a later main-actor turn, so the refused call is answered first, with its usual message.
    - Everything that waits on another app runs off the main thread.
  - **The launch context.** `src/api/launch.ts` holds what the app sent with the launch: preferences, `LaunchEnvironment` (built by `LaunchEnvironment.make`) and launch props. `environment` reads it through getters. `LocalStorage` (one JSON file) and `Cache` (one `cache.json` per namespace, least recently used dropped beyond its capacity) read and write in the worker, under the paths the environment names in fudge's support folder.
- **`fudge build <folder>` installs an extension** (`ExtensionBuilder` in `FudgeCore`).
  - It reads `package.json` (`ExtensionManifest`) and compiles every command's `src/<name>.{tsx,ts,jsx,js}` with esbuild into `<extensions>/<name>/dist/<name>.cjs`. The modules the host provides (`ExtensionBuilder.providedModules`) stay external.
  - It writes the build into `.staging-<name>-<uuid>` with `package.json` and `assets/` alongside, then swaps the whole folder into place (a previous install is moved to `.old-<name>-<uuid>` first, then deleted).
  - It never writes into the source folder. When the source has no `node_modules`, it installs the dependencies into a temporary folder (`npm ci --ignore-scripts`) and points esbuild at it with `NODE_PATH`.
  - Extensions live in `FudgePaths.extensionsDirectory`: `~/Library/Application Support/fudge/extensions`, or under `$FUDGE_SUPPORT_DIR`.
  - **The running app picks it up.** `ExtensionsWatcher` (core) watches the extensions folder through FSEvents, with file-level events. A path counts unless its first component under the folder starts with `.` (`.staging-*`, `.old-*`, `.DS_Store`), and a trailing 0.3 s debounce makes each install, rebuild or removal one reload: `LauncherModel.reloadExtensions()` (the installed extensions only, keeping the scanned applications, the query and the selection), the command hotkeys, and the Settings window if it's open. The menu's Reload Extensions also scans applications again. Snapshot runs don't watch.
- **The Makefile assembles the app bundle** (`make app`):
  - the `FudgeApp` binary becomes `Contents/MacOS/Fudge`
  - the `fudge` tool and esbuild's native binary go into `Contents/Helpers/`, where `ExtensionBuilder.locateEsbuild` finds esbuild next to the tool
  - `App/Info.plist` gets the version from `git describe`
  - `App/AppIcon.icon` (an Icon Composer icon) is compiled by `actool` into `Assets.car` and an `AppIcon.icns` fallback. That needs Xcode 26 or later.
  - the host and worker bundles go into `Contents/Resources/runtime/`
  - the helpers and the bundle are signed with `SIGN_IDENTITY`. From what `security find-identity -v -p codesigning` lists, the default is "fudge local signing", else the first `Apple Development:` identity, else ad hoc (see the README). It's picked by SHA-1, since two certificates can share a name. The `→ built` line names the identity, and with one, codesign's errors show and fail the build.
- **`make compat-scan DIR=<folder>` measures store compatibility statically** (`runtime/scripts/compat-scan.ts`). Every folder in `DIR` with a `package.json` and a `src/` is an extension, as in a checkout of raycast/extensions. Nothing is built or run.
  - `scripts/compat/scan.ts` turns each source file into JavaScript with esbuild, which drops type-only uses. Tests and mocks are skipped (`*.test.*`, `*.spec.*`, and `__mocks__/`, `__tests__/`, `test/` and `tests/` folders). It collects the API paths used through `@raycast/api` imports (`Clipboard.copy`, `Action.CopyToClipboard`) and the names imported from `@raycast/utils`.
  - Each path is checked against `createApiModule()`. A stub anywhere on the path makes it `missing`, a lowercase member's included. So do the two markers in `src/api/stubs.ts`: `UNAVAILABLE` is on the actions that render but fail when picked (`render-but-fail`), and `NOT_DRAWN` is on the components the app can't draw yet, listed at the end of `components.ts` (`not-drawn`). Whoever teaches the app to draw one removes it from that list in the same PR.
  - A path Raycast's types don't declare (`Color.Gray`, a mock's `showToast.mockResolvedValue`) is `not-raycast`: listed, but not a gap. `raycastDeclarations` (`scripts/raycast-types.ts`) reads the vendored types for that.
  - `@raycast/utils` is bundled from each extension's own dependencies, so its calls are invisible. `scripts/compat/raycast-utils.generated.ts` maps each of its exports to the API paths it needs, and an extension using one inherits them (`via @raycast/utils`). `scripts/compat/raycast-utils.ts` generates it from the `src/` files in the source map of the pinned `@raycast/utils` devDependency, with the same path extraction. `npm run generate` rewrites it, and `npm run typecheck` fails while it's stale.
  - The Markdown report counts extensions with no gaps, those lacking only APIs left out by design (AI, Browser Extension, and OAuth per decision D-50), and the rest. It ranks gaps by API and kind. `--json <file>` also writes each extension's gaps with their kind.
- **`runtime/vendor/raycast-api/index.d.ts` is Raycast's own type definitions** (MIT, notice alongside). It's the contract fudge implements. `make raycast-types` copies it unmodified from the `@raycast/api` release named by `RAYCAST_API_VERSION`. Never edit it by hand.

## Gotchas

- **Names must differ by more than case.** macOS file systems are case-insensitive, so no two products or targets may differ only by case. The tool's product is `fudge`, which is why the app's product is `FudgeApp`.
- **Proxies must return frozen properties untouched.** `createApiModule` wraps components to name missing members, but it leaves frozen constants (`Keyboard`, enums) unwrapped, or JavaScript throws.
- **Runtime TypeScript must be erasable syntax only** (`erasableSyntaxOnly`), because tests run it through type stripping. That rules out enums, namespaces, parameter properties and JSX in `.ts` files. Relative imports carry the `.ts` extension.
- **Compiled extension commands are CommonJS.** The worker loads them with `require`, which is the only way `Module._load` can hand them fudge's modules.
- **actool's paths must be absolute.** `xcrun actool` hands the work to a shared daemon, which resolves relative paths against its own working directory. That's whichever checkout started it, so with several worktrees, relative paths make one worktree's `make app` write the icon into another's `build/`. actool can also exit 0 when it compiled nothing, and it reports errors on stdout, so `make app` checks for `Assets.car` and then shows `build/actool.log`.
- **Apps opened from Finder don't get the shell's `PATH`.** That's why `Runtime.locateNode` checks `$FUDGE_NODE`, `Contents/Helpers`, Homebrew and `/usr/local` before `PATH`.
- **SwiftUI's `TextField` writes its unchanged text back** now and then, three times on ↵ before `onSubmit` and again when it loses the keyboard. Setters bound to a field must ignore writes that change nothing, or they'll redo work such as resetting the selection.
- **`.onAppear` runs once for the panel's lifetime**, not each time it's shown. Showing the panel (`LauncherModel.presented()`) and clicking a row ask for the keyboard back explicitly (`keyboardRequests`). `KeyboardFocus` (core) names the field each screen wants, and the views move it there through `nil`, because setting a `@FocusState` to the value it already holds does nothing, even when AppKit's first responder has moved.
- **Check the panel's layout without showing it:** `build/Fudge.app/Contents/MacOS/Fudge --snapshot out.png [--query text] [--activate]`. It renders the panel off-screen and transparent, then saves a PNG and quits. A snapshot run never activates (activation policy `.prohibited`, set in `main.swift` before launch), its windows refuse key status (`LauncherPanel.refusesKey`, `SettingsNSWindow`), and it installs no status item (fudge's or a menu-bar command's), global hotkey or key monitor, so it can't take anyone's typing or put a second icon in the menu bar. Just before saving, it prints `snapshot-state active=… appActive=… key=… canBecomeKey=…` to stderr; all four are false. In the command `--activate` opened, `--search text` types into its search field, `--dropdown value` picks a search bar dropdown value, `--actions` opens the action panel, and `--open-dropdown` opens the dropdown's panel (in a Form, its first Dropdown's; `--open-tags`, its first TagPicker's; `--open-date`, its first DatePicker's calendar). `--settings` renders the Settings window instead (`--settings :permissions` its Permissions page), `--onboarding [<step>]` the onboarding window, and `--accessibility allowed|missing` and `--login-item <status>` fix what Accessibility and Open at Login show, so nothing asks the system. The window blur doesn't render in snapshots. Run snapshots one at a time: several at once can miss their timing. `make run` opens the app with `open -n`, because LaunchServices would otherwise hand the open to a live snapshot run (same bundle id) and fail with -600; just before, it checks again that none of the user's own fudge is running.
- **Permission grants need a signing identity.** macOS ties Accessibility and Automation grants to the app's designated requirement. An ad hoc signature's is its cdhash, which changes with every build, so each ad hoc `make run` drops them; builds signed with an identity keep them. **The first signing with an identity shows a keychain prompt** that only a person can answer (Always Allow). Until someone has, `make app` waits on it, so build with `SIGN_IDENTITY=-` where nobody has. CI and releases have no identity and stay ad hoc. No certificate, key, name or team ID ever goes into the repo.
- **The local-network check reads the URL, not DNS.** A public name that resolves to a private address isn't caught. https mostly covers it, since a LAN device rarely has a certificate for a public name.
- **AppKit draws nothing inside an SVG `<a>` element**, so `RemoteImageDecoder.svgForDrawing` unwraps links before `NSImage(data:)` sees the SVG.
- **Tests must not touch the user's system.** Never trash, open, copy, read the selection, post key events or send Apple Events for real in a test, and smoke-run extensions with a throwaway `HOME`: commands do what they say.
- **Swift tests that build extensions need esbuild** from `runtime/node_modules`. `make test` installs it; without it, `swift test` skips those tests.
- **npm may block install scripts.** esbuild works without its postinstall step, so don't approve it just to silence the warning.

## Conventions

- Swift for the app and the tool. TypeScript only in `runtime/`, because extensions are JavaScript.
- Docs describe what exists. No roadmaps, status tables or TODO lists in committed files.
- Every setting has a control in the Settings window. `settings.json` and the other support files are never the documented way to change one.
- An on/off setting shown as a row in the Settings window is a switch on the right, with its label (and any explanation) on the left, as in System Settings. A column of on/off cells in a table, like the Commands page's Enabled, uses checkboxes, as do extensions' own Forms.
- Conventional commits (`feat:`, `fix:`, `chore:`, `docs:`), scoped by area where it helps, e.g. `feat(runtime): ...`, `feat(app): ...`, `feat(cli): ...`.
- `AGPL-3.0-or-later` everywhere. Files taken from MIT-licensed upstream keep their notice next to them. New dependencies must be AGPL-compatible.
- Third-party GitHub Actions are pinned to commit SHAs, with the version in a trailing comment.
- **A probe or hand check that launches a second fudge** which creates status items, windows or preferences runs from a copy of the bundle with a **different bundle id**, e.g. `plutil -replace CFBundleIdentifier -string io.github.jakeobsen.fudge.probe <copy>/Contents/Info.plist`. Builds with the same bundle id share the real app's preferences, whatever `HOME` or `FUDGE_SUPPORT_DIR` says, and that's how a probe once hid the user's menu bar icon. `--snapshot` runs are exempt: they create no status item, take no keyboard and write no preferences.
- **Help text, in the app and the README, is brief and says what a feature does, for an end user.**

## CI and releases

- **CI** (`.github/workflows/ci.yml`) runs `make lint` and `make test` on pull requests and pushes to `mainline`. `swift test` compiles every target, so the app's code is checked, but the app bundle is not assembled.
- **The release workflow** (`.github/workflows/release.yml`) is the only place the app bundle gets built. It runs on a pushed `v*` tag: tests, then `make app CONFIG=release VERSION=<tag>`, then the bundle zipped with `ditto` and uploaded as a workflow artifact.
